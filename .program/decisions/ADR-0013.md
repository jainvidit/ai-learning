# ADR-0013 — `memory: project` is banned outright in this program

**Status:** accepted (2026-07-26) · **Scope:** every `dream-*` role file, both copies
(`.program/roles/` authoritative, `C:\Users\jainv\.claude\agents\` loaded) ·
**Inputs:** controlled A/B on `zz-memtest-with`/`zz-memtest-without`, fresh runtime tool
enumerations of the five affected roles, agent-registry read before and after the edit

## Context

Five roles declared themselves READ-ONLY in prose and carried an explicit `tools:`
allowlist containing no Write and no Edit:

| Role | Declared `tools:` |
|---|---|
| `dream-reviewer-primary` | Read, Grep, Glob, Bash, ToolSearch |
| `dream-reviewer-secondary` | Read, Grep, Glob, Bash, ToolSearch |
| `dream-reviewer-adversarial` | Read, Grep, Glob, Bash, ToolSearch |
| `dream-ledger-auditor` | Read, Grep, Glob, Bash |
| `dream-ledger-auditor-deep` | Read, Grep, Glob, Bash |

All five also carried `memory: project`. At runtime all five had **Write and Edit**.

## Decision

**`memory: project` — and any `memory:` key — is banned outright in this program. Not
just on the five roles above: on every `dream-*` role, present and future.**

The key silently grants Write and Edit regardless of an explicit `tools:` allowlist. The
allowlist is not a ceiling; `memory:` adds to it. Nothing in the role file warns you, and
nothing in the runtime tool list explains where the extra tools came from.

### How this was established

Three independent confirmations, in increasing strength:

1. **Fresh runtime enumeration** of each of the five roles listed Write and Edit
   alongside the declared tools.
2. **Registry read before and after** removing the line: the extra tools disappeared.
3. **Controlled A/B — the decisive one.** Two throwaway agents, byte-identical but for
   the memory key, both declaring `tools: Read, Grep, Glob, Bash`:

   | Probe | frontmatter | runtime tools |
   |---|---|---|
   | `zz-memtest-with` | `memory: project` | Read, Grep, Glob, Bash, **Write, Edit** |
   | `zz-memtest-without` | *(no memory key)* | Read, Grep, Glob, Bash |

   One variable, one difference in outcome. The mechanism is `memory:`, not model, not
   effort, not prose, not some unrelated permission-mode interaction. Both probes were
   deleted after the run.

### Remediation applied

`memory: project` removed from all five role files in both locations — one line deleted
per file, nothing else touched (`git diff --stat` = 5 files changed, 5 deletions). All
five pairs verified byte-identical afterwards. Post-edit runtime lists show the declared
tools only.

### Enforcement

`dream-ledger-auditor` gains a standing check (check 11), inherited verbatim by
`dream-ledger-auditor-deep`: **any `dream-*` role file carrying a `memory:` key is a
BLOCKING finding**, reported with the role name, both file paths, and the fact that the
key grants Write and Edit silently. Blocking means the director stops and fixes before
dispatching that role — this is not an advisory drift note like the model/effort checks.

The check is placed on the auditor because the auditor already reads both role
directories every run for mirror-drift (check 8), so a memory key cannot be reintroduced
by hand-editing a role file without the next audit catching it.

## Consequence

- No `dream-*` role gets persistent memory. Roles that need to carry state across
  dispatches do it through the ledger, which is auditable, or not at all.
- The tools allowlist in a role file is now a reliable statement of *at most what a role
  can do* — but only because no role has a memory key. Add one back and the allowlist
  becomes decorative again.
- A tools declaration was never a security boundary and still isn't. See ADR-0014: Bash
  alone is sufficient to write anywhere, so removing Write/Edit narrows the surface
  without closing it. The only real enforcement is permission deny rules.

## If wrong

If a role turns out to genuinely need memory, this ADR must be reopened explicitly rather
than worked around — and the reopening has to state how Write and Edit will be denied by
permission rules for that role, since the frontmatter cannot deny them. If a future
Claude Code version decouples `memory:` from Write/Edit, re-run the A/B before relaxing
anything: the probes are trivial to recreate (two role files identical but for the key,
each asked to enumerate its own tools without using any).
