# ADR-0017: CP-05 hash-input domain — enumerate distinguishable types; reject outside the domain

Status: accepted 2026-07-27 (director gen40, owner-directed: "do not let the fix land
against an unrevised spec")
Item: ROOT.1.1.3. Spec: content-pipeline.md REQ-CP-05 scenario 1.

## Problem

CP-05 s1 says "Given an item whose content changes in any way … then its itemRevision
hash changes" without stating which JS types must be distinguishable. The first
adversarial review (2026-07-27) proved the gap is load-bearing: the shipped
canonicalStringify silently collapses NaN/Infinity→null, Date/Map/Set→{}, embeds literal
`undefined` for function values, and RangeErrors on cycles. "Changes in any way" is
unfalsifiable over the open set of JS values — no test suite can cover an unenumerated
domain, so the criterion passed review while the guarantee was false.

## Both readings

**A — coerce-and-broaden:** extend canonicalization to encode every JS type distinctly
(tag Dates, serialize Maps/Sets, encode NaN/±Infinity, hash cycles structurally).
**B — enumerate-and-reject:** define the hash-input domain as the JSON data model; any
value outside it throws `TypeError` with a path to the offending key.

## Decision: B

- **Least irreversible.** A throw can later be relaxed into an encoding for any type we
  choose to admit (B→A per-type is additive); values already silently collapsed into
  published immutable bundles can never be disentangled (A after shipping B's gap is
  data-safe; the reverse is not). CP-04 immutability builds on these hashes.
- **Most consistent with adjacent shards.** Bundle content is JSON on disk
  (`public/content-bundle/<version>/*.json`, CP-04); beats come from compiled MDX/JSON
  sources; CP-06's whole posture is fail-loudly-in-CI. A non-JSON-representable value in
  content is a build bug, and B makes it a visible one at build time instead of a silent
  hash collision at migration time.

## The domain (normative, mirrored into the shard)

HASHABLE: `null`; booleans; finite numbers (with `-0` normalized to `0`, matching
JSON.stringify); strings; arrays of hashable values; plain objects with string keys and
hashable values, key order irrelevant, keys with `undefined` values omitted (ratified
ROOT.1.1.3 fix-cycle behavior, unchanged). Distinct values within this domain MUST
produce distinct canonical forms.
REJECT with TypeError naming the JSON path: `undefined` (except as an omitted object
value), functions, symbols, BigInt, NaN, +/-Infinity, Date, Map, Set, RegExp, typed
arrays, class instances (non-plain prototypes incl. null-prototype accidents beyond
Object.create(null), which is admitted as plain), and circular references (detected,
reported as a cycle — never a bare RangeError).
`__proto__` as an id or key: must be handled without prototype-accessor loss (null-
prototype map or Map internally); silently dropping an entry is a domain violation.

## Consequences

- Shard REQ-CP-05 amended (hash-domain clause + scenario 3); scenario 1's "in any way"
  now scoped to the enumerated domain — testable and falsifiable.
- ROOT.1.1.3 fix cycle implements B; acceptance criteria updated to cite the enumeration.
- REJECTED.md checked: nothing reopened (no prior decision on hash domains exists).
- Logged in DECISIONS-PENDING.md per PART 9 Rule 1: if the other reading (A) is ever
  preferred, the change is additive (admit types one by one with explicit encodings),
  requiring a new ADR + migration-map guidance for any hash whose input newly admits a
  previously-rejected type.
