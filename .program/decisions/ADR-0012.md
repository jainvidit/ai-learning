# ADR-0012 — Duplicate-scheduler storm: three concurrent launch paths, no mutual exclusion

**Status:** accepted (2026-07-26) · **Inputs:** `events/ROOT.jsonl` (~36 standdown events,
gens 2–36), `.program/handoffs/ROOT-15.md`, `.program/audits/2026-07-25T1440-ledger-audit.md`,
`%TEMP%\director-{1..38}.log`, 53 session records under
`C:\Users\jainv\.claude\projects\C--Users-jainv-workplace-ai-learning-app\`,
PSReadLine `ConsoleHost_history.txt:325-342`, `.claude/daemon/roster.json`

## Context

Between 2026-07-25 07:43Z and 16:46Z the program ran 38 director generations. Roughly 36
of them did no work: each started, detected a live incumbent, appended a standdown event,
and exited. The handoffs and the routine audit attributed this to a "supervisor relaunch
interval" of ~4–6 minutes running against a ~30-minute rotation budget, and the standing
recommendation on record was to raise that interval or key relaunch on the
`DIRECTOR_HANDOFF_WRITTEN` marker.

That diagnosis was wrong about the cause, and the remediation it implied would not have
worked.

## Decision

**Root cause: three concurrent launch paths for `dream-director`, with no mutual exclusion
between them. Not the relaunch interval.**

1. **Interactive `--agent` session.** `claude --model fable --agent dream-director
   --dangerously-skip-permissions`, started 07:43:57Z (PID 37892). This became the gen39
   incumbent and was still running 29 hours later, holding the scheduler role.
2. **Headless PowerShell loop.** A `for ($i = 1; $i -le 200; $i++)` loop typed directly at
   an interactive prompt — never saved to any file, which is why no supervisor script
   exists in the repo or the user profile. Each iteration ran
   `claude -p $Resume --model fable --permission-mode acceptEdits`, tee'd stdout to
   `%TEMP%\director-$i.log`, then ran `git add -A; git commit -m "director gen $i"
   --allow-empty` and `Start-Sleep -Seconds 5`. It produced the 25 sessions bearing
   `entrypoint: "sdk-cli"` / `promptSource: "sdk"`. It stopped at generation 38, short of
   its own 200-iteration bound, when its console was closed.
3. **Background fork registered under the same name.** Job `e32c9752` in
   `.claude/daemon/roster.json`, a `--fork-session` of the interactive session, registered
   with `seed.name = "dream-director"` and `permission-mode bypassPermissions`.

No path was aware of the others. Nothing consulted the ledger, a lock, or a pidfile before
launching. Three independent things could each believe they exclusively owned item files,
git, and dispatch.

**There was no interval to raise.** The loop relaunched 5 seconds after the previous
`claude -p` exited. The apparent 4–6 minute cadence was simply how long each headless
director survived — and because a duplicate that stands down exits quickly (~2 min), the
failure was self-accelerating rather than fixed-period. Raising a nonexistent interval
above the rotation budget would have changed nothing. The loop's one guard,
`if ($out -notmatch 'DIRECTOR_HANDOFF_WRITTEN')`, only printed a warning; it never delayed
or stopped the relaunch. Directors correctly inferred this and deliberately suppressed the
marker to avoid provoking further relaunches — a mitigation that was reasoning against a
supervisor that did not exist.

Side effect worth recording: the loop's own `git add -A; git commit --allow-empty` ran
between every generation, so an unattended shell was committing the working tree
independently of any director's timer commits. The `director gen N` commits in history are
the loop's, not the directors'.

## What worked

- **The standdown mechanism worked and prevented ledger corruption.** Every duplicate
  performed the liveness check (quiet ledger for one interval AND no commits for 10+ min),
  found the incumbent live, wrote one append-only `divergence`/standdown event, and
  exited without dispatching, without writing item files, and without git. No
  double-dispatch and no lost-update corruption resulted from the storm. The routine audit
  at 13:40Z passed with no `owner_compacted` anomalies. The two known duplicate-writer
  incidents (ROOT.1.2.1's duplicate implementer, gen2's orphaned reviewer writing under
  gen3's name) came from orphaned subagents outliving their parent session — a distinct
  fault class, already contained and dispositioned.
- **The prohibition on dispatching `dream-director` as a subagent held.**
  `grep -rl dream-director .program/ledger/events/` returns zero matches: no spawn event
  in any of the 57 event files names it. All 7 Agent-capable roles (2 coordinators,
  5 implementers) carry the explicit launch-only exclusion, and it was never violated. The
  breach came from the OS shell, entirely outside the agent graph.

  This is worth keeping in view because those role files are candid that the guard is
  prose only — the `agent_type` allowlist constrains a main-thread agent, not a subagent.
  The instruction-only guarantee held under 38 generations of pressure, but it is not
  enforced, and the storm demonstrated that the unenforced surface is the OS, not the
  roster.

## Consequence

The supervisor loop is abandoned. There is no automated relauncher and no supervisor
process. The director is launched by hand and rotated by hand.

- Sanctioned launch, and the only one: a **single interactive**
  `claude --agent dream-director`.
- `.program/prompts/resume.md` is moved to `.program/prompts/resume.md.disabled` and
  carries a header stating that running it headlessly starts a scheduler that believes it
  owns the ledger. The file is a loaded gun: its content is a complete scheduler seed, and
  a single `claude -p` against it re-creates the fault.
- Remediation baseline established 2026-07-26: PID 37892 (gen39 incumbent), the
  `e32c9752` background fork (PIDs 4896, 32936) killed; `dream-director` deregistered from
  `.claude/daemon/roster.json`. The Claude Code daemon itself was left alone (it manages
  background jobs and auth refresh only — it is not the "supervisor" the handoffs blamed;
  `daemon.log` shows nothing but auth refreshes across the entire storm window).

## Correction to the record

`.program/handoffs/ROOT-15.md` reports 14 standdowns. That was a mid-storm snapshot taken
by gen15. The actual total in `events/ROOT.jsonl` is ~36 across 38 generations
(`director-duplicate-standdown-2` … `-36`, plus `director-relaunch-16 (standdown-15)`).
The handoff's figure is not wrong for the moment it was written; it is not the total.

The "supervisor" named throughout the handoffs, the standdown events, and audit cycle 1
never existed as described. Statements in those documents about supervisor cadence and
supervisor behaviour are inferences from observed relaunches, not observations of a
supervisor, and should be read as superseded by this ADR. Their factual content —
timestamps, standdown counts, liveness observations — remains authoritative.

## If wrong

If duplicate directors appear again with no interactive launch and no headless loop
running, the assumption that these three paths were exhaustive is wrong. Check first for a
fourth registration path: `.claude/daemon/roster.json` workers, `CronList` /
`.claude/scheduled_tasks.json`, and Windows Task Scheduler (all three were verified clean
on 2026-07-26). Preserve `%TEMP%\director-*.log` and the session records under
`.claude/projects/`; `entrypoint` and `promptSource` on the first user record of each
session file are what distinguish a typed launch (`cli`/`typed`) from a programmatic one
(`sdk-cli`/`sdk`), and that distinction is what identified path 2.
