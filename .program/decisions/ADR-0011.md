# ADR-0011 — Beat segmentation, beatId derivation, sidecar revisions, bundle versioning

**Status:** accepted (autonomous, coordinator decision within delegated scope)
**Item:** ROOT.1.1 · **Date:** 2026-07-25
**Context:** `.program/interfaces/beat-model.md` states the beatId derivation algorithm is
the beat compiler's (ROOT.1.1's) choice — "any derivation satisfying S1–S4 conforms."
This ADR fixes that choice at coordinator level so no leaf makes a contract-adjacent
decision silently (six-point leaf test, point 4).

## Decisions

1. **Segmentation.** A lesson MDX file splits into beats at two structural boundaries:
   exercise anchors (`<Exercise id="…" />`) and `h2` headings. Each exercise anchor
   yields one beat whose `type` maps 1:1 from the exercise's type in `exercises.json`
   (quiz→quiz, playground→playground, terminal→terminal, challenge→challenge). Each
   contiguous prose region yields one `prose` beat per h2 section.
2. **beatId keys (lesson-scoped, authored-identity-based):**
   - exercise beats: `ex:<exerciseId>` (the authored exercise id)
   - prose beats: `prose:<slug-of-leading-h2>`
   - a leading segment before the first h2: `prose:intro`
3. **Duplicate keys within a lesson are a build failure** (no `-2` suffixing — suffixes
   re-introduce positional identity and break S3).
4. **Conformance argument:** S1 — editing text inside a beat changes neither its heading
   slug nor an exercise id; S2 — keys are a pure function of source, no counters or
   timestamps; S3 — keys are never positional; S4 — titles/minutes/objectives/tier are
   not in any key. Renaming a heading or exercise id is I3 (retire + create), which the
   contract sanctions and routes to migration maps (REQ-CP-05 scenario 2).
5. **Widget beats deferred.** Custom interactive components (TokenVisualizer,
   NextWordGame) remain INSIDE prose beats in Phase 0. Standalone `widget` beats need an
   authoring convention owned by the curriculum lane; the compiler emits no `widget`
   beats yet. (Additive later; no beatId churn for existing beats.)
6. **itemRevision stays OUT of the compiled Beat shape.** The Beat field set is frozen by
   REQ-CP-02/beat-model.md; adding a field would trigger the steward change protocol.
   Instead the bundle carries a sidecar `revisions` map keyed by item/beat id
   (REQ-CP-05), which beat-model.md already declares out of its scope.
7. **Bundle version id = short content hash** over the canonical bundle payload.
   Deterministic (rebuilding unchanged content yields the same version), and
   immutability is auditable: the emitter MUST fail if a version directory exists with
   differing bytes (REQ-CP-04 scenario 2).

## Alternatives rejected

- Ordinal beatIds (`beat-1`…): fails S3 explicitly (beat-model.md says so).
- Content-hash beatIds: fails S1 (prose edits would change identity; identity vs
  revision is exactly the split REQ-CP-05 draws).
- Prose beats keyed to adjacent exercise ids (`before:<exId>`): fails S3 when the
  neighboring exercise is deleted.
- Timestamp/build-counter version ids: violates S2-style determinism and makes
  immutability unauditable.

## If wrong

Heading-slug keys that prove too churn-prone are retired per I3 with migration-map
entries; ADR-0005's additive-fallback pattern applies. Nothing here narrows the
contract, so consumers are unaffected by a later widening.
