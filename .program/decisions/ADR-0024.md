# ADR-0024: REQ-LX-07 s3 "any beat entering view" — beat entry-mode domain enumeration

Status: ratified 2026-07-28.
Item: ROOT.7.3.6. Spec: lesson-experience.md REQ-LX-07 scenario 3.

## Context

REQ-LX-07 s3 says "Given **any beat entering view**, when telemetry is checked, then a beat_viewed event was recorded." The universal quantifier "any beat entering view" was unfalsifiable over an unenumerated domain: no test suite can cover an open set of entry modes, so the criterion could pass review while the guarantee was false for unnamed modes.

The unfalsifiable-criteria survey (.program/audits/2026-07-27T0540-unfalsifiable-criteria-survey.md, row 6) identified this as a clear match — a universal phrase over an unenumerated domain (named as "beat entry modes: scroll, jump, resume, restore"). This is the same failure mode as CP-05 s1 ("content changes in any way"), which passed review while false and was fixed by enumeration in ADR-0017. Following that precedent (ADR-0017's closed-world pattern: enumerate the domain, reject outside it, relaxation is additive via new ADR), this decision enumerates the beat entry modes bound by REQ-LX-07 s3.

## The enumerated beat entry-mode domain (normative)

REQ-LX-07 s3 applies to exactly SEVEN beat entry modes in the ai-learning-app:

### 1. Scroll entry — natural scrolling into viewport
- **Mechanism:** User scrolls the lesson page naturally; a beat crosses the 50% viewport threshold and is considered "in view."
- **Source:** REQ-LX-01 s2 (dwell-based frontier advancement: "50%-viewport/2s dwell"), REQ-LX-01 s1 (all beats mount at full height, styled as future)
- **Current state:** MODIFIED — beats past frontier dimmed (~60% opacity); frontier advances on dwell or Continue
- **s3 obligation:** When a beat crosses 50% viewport during scroll, then a `beat_viewed` event is recorded (once per beat per session; duplicates idempotent or suppressed).
- **Testable:** Render lesson, programmatically scroll to a beat not yet viewed, wait for 50% intersection, verify event emitted.

### 2. Rail jump navigation — direct jump from progress rail
- **Mechanism:** User clicks a beat node in the sticky progress rail to jump directly to that beat.
- **Source:** REQ-LX-04 s4 ("Given the rail, when a beat is clicked in it, then the view jumps to that beat")
- **Motion interplay:** Smooth-scroll in default motion preference; instant jump under `prefers-reduced-motion` (frontend-platform.md REQ-FP-03). Either way, the beat enters view.
- **Current state:** MODIFIED — rail doubles as jump-nav in both lesson-in-progress and revisit mode
- **s3 obligation:** When a rail node is clicked and the view lands on the target beat, then a `beat_viewed` event is recorded.
- **Testable:** Render lesson, click a rail node, verify view lands on beat and event emitted.

### 3. Resume from stored position — dashboard resume-to-beat deep link
- **Mechanism:** User clicks "Jump to where you left off" chip on dashboard; navigation completes to the exact stored `beatId`.
- **Source:** REQ-LX-07 s2 ("Given a resume action from the dashboard chip, when navigation completes, then the view lands on the exact stored beat ID")
- **Current state:** NEW — no resume affordance exists today
- **s3 obligation:** When resume navigation completes and the target beat enters view, then a `beat_viewed` event is recorded.
- **Testable:** Store a resume position, navigate away, click resume chip, verify view lands on stored beat and event emitted.

### 4. Initial page load — lesson opens, beats mount and enter viewport
- **Mechanism:** Lesson page renders; the top beat(s) are in viewport on mount (beat 0 warm-up if present, else beat 1 prose/exercise).
- **Source:** REQ-LX-01 s1 ("All beats mount on load at full height"), REQ-LX-04 (warm-up beat 0 rendered first when due reviews exist)
- **Current state:** REPLACED — lesson page is now beat flow + rail (single-MDX render removed)
- **s3 obligation:** When the lesson page loads and the initially-visible beat(s) mount in viewport, then a `beat_viewed` event is recorded for each.
- **Testable:** Navigate to lesson URL, verify beat(s) in viewport on mount emit events.

### 5. Continue button navigation — smooth-scroll to next beat
- **Mechanism:** User clicks Continue (or "Skip for now" on incomplete exercise); view smooth-scrolls and focus moves to the next beat.
- **Source:** REQ-LX-01 s3 ("Given Continue on an incomplete exercise beat … clicking it moves scroll+focus onward")
- **Motion interplay:** Smooth-scroll in default preference; instant jump under `prefers-reduced-motion` (REQ-FP-03).
- **Current state:** MODIFIED — Continue relabels "Skip for now" on incomplete exercise, rail marks amber
- **s3 obligation:** When Continue triggers navigation and the next beat enters view, then a `beat_viewed` event is recorded.
- **Testable:** Click Continue, verify view lands on next beat and event emitted.

### 6. Keyboard navigation — j/k and Alt+↑/↓ beat navigation
- **Mechanism:** User presses j (next beat), k (previous beat), Alt+↓ (next), or Alt+↑ (previous) to navigate between beats.
- **Source:** REQ-LX-04 s5 ("Keyboard: j/k and Alt+↑/↓ beat nav, suppressed inside terminal/playground inputs. Reduced motion: instant jumps.")
- **Suppression rule:** Keys pass through as text when focus is inside a terminal or playground input (no navigation).
- **Motion interplay:** Instant jumps under `prefers-reduced-motion` (REQ-FP-03); smooth-scroll otherwise.
- **Current state:** NEW — keyboard beat nav not implemented today
- **s3 obligation:** When keyboard navigation lands on a beat, then a `beat_viewed` event is recorded (suppression rule applies: no event if key passes through as text).
- **Testable:** Press j/k outside input, verify view lands on next/prev beat and event emitted; press j/k inside terminal input, verify no nav and no event.

### 7. State restore after page refresh — beat already in viewport on hydration
- **Mechanism:** User refreshes the page (F5 / reload); the view position is restored by the browser, landing on a beat already in viewport.
- **Source:** REQ-LX-06 s1 ("Given a passed quiz and a page refresh, when the lesson re-renders, then the quiz frame shows Passed with its stored best score" — exercises hydrate from stored progress, implying the page survives refresh)
- **Distinction from resume:** Resume is an explicit dashboard action targeting a stored `beatId`; state restore is browser-level scroll restoration on the same lesson without navigation away.
- **Current state:** MODIFIED — ExerciseFrame hydrates from stored progress (refresh never renders passed as untouched)
- **s3 obligation:** When the page reloads and a beat is in viewport on hydration, then a `beat_viewed` event is recorded (idempotent with prior views or suppressed if already recorded this session).
- **Testable:** Load lesson, scroll to beat 5, refresh, verify beat 5 still in view and event emitted (or idempotently suppressed).

## Closed-world rule

**The enumeration above is exhaustive.** Any beat entry mode not on this list is NOT bound by REQ-LX-07 s3 until explicitly added by a future additive ADR. Implementing a new navigation/entry mode without amending this ADR first is a spec violation.

The spec obligation is no longer "any beat entering view emits an event" (an open list) but "verify that each mode on the normative list satisfies the s3 obligation: `beat_viewed` event recorded when the beat enters view."

## Decidable default for unenumerated modes

If a future navigation mode is implemented that is not on this list (e.g., search-driven navigation, deep-link anchor from external site, browser back/forward history navigation), the **default is to emit the `beat_viewed` event** until an additive ADR explicitly excludes it. This fail-toward-telemetry default ensures observability and prevents silent gaps in the event log.

## Consistency with beat-model.md persistent-beat ruling (ROOT.7.1, 2026-07-25)

The beat-model.md interface document (lines 169–255) contains a steward ruling (ROOT.7.1, ratified 2026-07-25) on the narrow reading of the `persistent: true` requirement. The ruling states that **persistence applies ONLY to beats with genuine session identity** (terminal sessions, agent runs, session-backed SSE widgets) — NOT to playground beats, whose SSE transport is request-scoped. The deciding test is "is there a session identity to restore?" rather than "does bytes-over-time reach the client?"

**Persistent beats and entry modes — no contradiction.** A persistent beat (e.g., a terminal beat with `persistent: true`) stays mounted across beat transitions within the lesson (REQ-LX-03 scenario 1), never receives `display:none`, and never collapses to zero height. Its DOM instance remains in place while the user navigates to other beats. The `beat_viewed` event obligation applies uniformly to persistent beats:

- **Initial appearance:** When a persistent beat first enters the viewport (via any of the seven modes above), a `beat_viewed` event is recorded.
- **Subsequent scrolling:** If the user scrolls away from a persistent beat and then scrolls back to it, the beat never unmounted (it stayed mounted per REQ-LX-03), but it re-enters the viewport. The event obligation is per-viewport-entry, not per-mount. If the telemetry system suppresses duplicate `beat_viewed` events for the same beat within a session (idempotent emission), then the second viewport entry may be suppressed. If not suppressed, a second event is recorded. **This is an implementation decision for ROOT.2.1 (Event Log and Projections), not a contradiction of the persistent-beat ruling.**
- **No portal-move events:** The persistent-beat ruling describes portal-slot obligations (PersistentTerminalHost portals xterm instances into beat slots and the dock — REQ-TX-02). When a terminal instance is moved from a beat slot to the bottom dock or back, the beat slot itself is still mounted (REQ-LX-03), and the instance is merely portaled. **This is not a beat entry mode** — the beat did not enter the viewport; the terminal instance changed destination. No `beat_viewed` event is triggered by portal moves.

**Citations confirming no contradiction:**
- beat-model.md lines 160–163: "For any beat with `persistent: true`, the beat's DOM instance must: Stay mounted across beat transitions within the lesson (REQ-LX-03 scenario 1); Never receive `display:none` styling (REQ-LX-03 scenario 2); Never collapse to zero height (REQ-LX-03 scenario 2)."
- lesson-experience.md REQ-LX-03 s1: "Given a running terminal beat, when the learner scrolls or advances to other beats in the lesson, then the terminal's DOM instance remains mounted with its dimensions intact."
- The ruling at line 189: "The requirement's obligations are session-survival obligations, not stream-handling ones: stay mounted across beat transitions and route changes, never `display:none`, never zero height."

**No entry mode contradicts the persistent-beat ruling.** The ruling constrains which beats may be marked `persistent: true` (session-identity test) and what happens to their mounting lifecycle (stay mounted, never hidden). It does not exempt persistent beats from telemetry obligations when they enter the viewport, and it does not introduce a new entry mode. Every enumerated mode above applies uniformly to both persistent and non-persistent beats.

## Per-mode falsifiable restatement of REQ-LX-07 s3

For each mode in the enumerated domain:

1. **Event emission:** When the beat enters the viewport via this mode, then a `beat_viewed` event is emitted to the event log with the `beatId` and session context.
2. **Event shape:** The event payload is defined by ROOT.2.1 (Event Log and Projections, explicitly deferred by beat-model.md line 332–336). This ADR does not constrain the event shape — only that the event is recorded.
3. **Idempotency:** If the same beat enters the viewport multiple times in one session (e.g., scroll away and back), whether duplicate events are suppressed is an event-log design decision (ROOT.2.1), not a per-mode variation. All modes treat idempotency identically.

These obligations are testable per mode: trigger the mode, verify the beat enters view, verify the event appears in the log.

## Relaxation path

To admit a new beat entry mode:
1. Write an additive ADR that: (a) names the new mode (mechanism, source REQ, owning item), (b) confirms s3 obligation applies or states an exception with rationale, (c) updates this ADR's enumeration section by appending the new entry.
2. Amend lesson-experience.md additively to reference the new ADR.
3. Implement the mode with `beat_viewed` emission or document the exception.

Migration guidance: if a mode was implemented without `beat_viewed` emission before being added to this list, its addition to the domain obligates retrofit or explicit exception.

## What was NOT enumerated and why

- **Browser back/forward navigation:** Not explicitly named in any spec requirement as of 2026-07-28. If implemented, falls under the decidable default (emit event) until explicitly added to this list or excluded.
- **Deep-link anchors from external sites:** No spec requirement for external deep-linking to beats. If implemented, falls under the decidable default.
- **Search-driven navigation:** No spec requirement for in-lesson search as of 2026-07-28 (Phase 3 not yet scoped). If implemented, falls under the decidable default.
- **Portal slot moves (persistent beats):** When a terminal instance is moved between a beat slot and the dock, the beat itself does not enter view (it stayed mounted). Not a beat entry mode, so no event obligation.
- **Beat unmount/remount cycles (non-persistent beats):** If a non-persistent beat unmounts and later remounts (e.g., due to virtual scrolling or conditional rendering), the remount + viewport entry is equivalent to initial page load (mode 4). Covered by existing modes; no new mode needed.

## Consequences

- lesson-experience.md REQ-LX-07 s3 amended additively to quantify over the enumerated modes (domain clause added under s3).
- Acceptance tests for s3 are now mode-by-mode checks: each enumerated mode must pass event-emission verification.
- Implementing a beat entry mode outside this list without an additive ADR is a spec violation (caught at review or by grep-based audit).
- The unfalsifiable "any beat entering view" phrase is now bounded and testable.
- ROOT.2.1 (Event Log and Projections) owns the `beat_viewed` event shape and idempotency policy; this ADR only obligates that the event is recorded per mode.
