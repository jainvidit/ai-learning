# ADR-0016 — Serializing concurrent file ownership; ADR-0007 #1's no-overlap claim was wrong

**Status:** accepted (2026-07-26) · **Supersedes in part:** ADR-0007 #1 ·
**Evidence:** `.program/audits/ownership-overlap-scan/2026-07-26-glob-overlap-scan.txt`
(and the reproducible `scan-globs.py` beside it)

## Context

`file_ownership` globs must not overlap between concurrently active items — one of the
"violating these corrupts the program" invariants in the director's operating prompt. It
was being violated.

At remediation time three items were `in_progress` and all held `package.json`:
**ROOT.7.1** (contract steward), **ROOT.1.1** (content pipeline), **ROOT.1.1.4** (bundle
emitter) — plus **ROOT.1** as their Phase-0 parent. ROOT.7.1 additionally held
`src/lib/schema.ts` concurrently with ROOT.1.

ADR-0007 #1 asserted the opposite:

> ROOT.7.1 (contract steward) takes over `src/lib/schema.ts`, `.program/interfaces/**`,
> `package.json` when ROOT.1.2/Phase 0 close **(no concurrent overlap: it activates on
> their completion)**.

### Why the claim was wrong

**The ADR's prose and the ledger's edges disagreed, and nothing reconciled them.** The
prose says ROOT.7.1 activates when "ROOT.1.2 **/ Phase 0**" close — two conditions. The
item's `depends_on` encoded only `[ROOT.1.2]`. So when ROOT.1.2 closed on 2026-07-25 at
13:59:30Z, the steward activated and took `package.json` and `src/lib/schema.ts` **while
Phase 0 was still open and three Phase-0 items still owned `package.json`.** The
parenthetical "no concurrent overlap" was a *prediction* about a schedule the ledger did
not actually implement — asserted at genesis, never re-checked against the graph, and
false from the moment the steward activated.

Three compounding reasons it went unnoticed:

1. **A prediction was recorded as a property.** "No concurrent overlap" was written as a
   settled fact in an accepted ADR, so later agents treated it as one rather than as a
   constraint requiring an edge.
2. **The exemption made ROOT.7.1 look out of scope.** ADR-0007 puts ROOT.7 "outside the
   phase order" as a standing service. Being exempt from *phase ordering* was read as being
   exempt from *ownership serialization*. It is not: standing items are exactly the ones
   that overlap everything, because they never close.
3. **Auditor check 5 only compares concurrently ACTIVE items.** It would have caught this,
   but the steward's overlap looked benign to inspection — it never actually wrote a source
   file, so no symptom ever appeared.

### It was never exercised

The steward wrote no source file in either batch. Batch 2's `batch_end` event
(2026-07-25T19:08:00Z) records `src/lib/beats.ts`, `src/lib/schema.ts`, `package.json`,
`package-lock.json` all with **unchanged mtimes**; every batch-2 change was ledger-territory
doc prose. Its only non-ledger artifact is `eslint.config.mjs`, which no other item owns.
So this was a latent invariant violation, not a corruption — the same shape as the review
guarantee in ADR-0014.

## Decision

**Narrow the globs. Do not add serializing edges to a standing item.**

Both remedies were available; narrowing is correct here because the overlap was *stale
ownership*, not genuine contention:

- `.program/interfaces/**` and `eslint.config.mjs` **had** transferred to the steward at
  ROOT.1.2 closure. That transfer is real and correct.
- `src/lib/schema.ts`, `package.json`, `package-lock.json` had **not** — the Phase-0 chain
  is still actively writing them. Listing them on ROOT.7.1 asserted a transfer that had not
  happened.

Adding `depends_on` edges from the Phase-0 writers to ROOT.7.1 was rejected: ROOT.7.1
"closes only when ROOT.5 closes", so anything made to depend on it would be blocked for the
rest of the program. Serializing edges do not work against an item that never terminates —
which is the structural lesson here.

Applied to `ROOT.7.1.md`:

```yaml
depends_on: [ROOT.1.2, ROOT.1.8]        # was [ROOT.1.2]
file_ownership: ["eslint.config.mjs", ".program/interfaces/**"]
file_ownership_deferred: ["src/lib/schema.ts", "package.json", "package-lock.json"]
```

`ROOT.1.8` is the Phase 0 Gate, whose own `depends_on` covers every Phase-0 sibling. So
`depends_on: [ROOT.1.2, ROOT.1.8]` now encodes in edges exactly what ADR-0007's prose
said in words: *ROOT.1.2 closes **and** Phase 0 closes.* The three deferred paths transfer
to `file_ownership` when ROOT.1.8 closes. Until then a steward request against them is
parked in the steward backlog, not served — stated in the item's `resume_hint` so a fresh
steward generation cannot miss it.

`file_ownership_deferred` is a new key. It is deliberately NOT `file_ownership`, so
auditor check 5 does not see it and no future reader mistakes a scheduled transfer for a
current one.

### Result

Live unserialized overlaps: **3 → 0.**

The four remaining active-pair overlaps are parent/child (ROOT↔ROOT.7.1,
ROOT.1↔ROOT.1.1, ROOT.1↔ROOT.1.1.4, ROOT.1.1↔ROOT.1.1.4), which are legitimate — a parent
owns the union of its children's paths as a scheduling container and does not write
concurrently with them.

## The 57-item scan

Every pair of the 57 items was tested, not just the active set: 1596 pairs, of which **151
share at least one concrete path**. Each was then classified by whether some mechanism
actually orders the two items. Four mechanisms count as serializing, and the first scan
missed the last three — worth recording, because each is a real ordering guarantee that
`depends_on` alone does not express:

| Mechanism | Why it orders |
|---|---|
| `depends_on` transitive closure | direct, and `blocks` normalized into it |
| Phase order | ROOT.1–ROOT.5 strictly ordered (ADR-0001); cross-phase pairs cannot be active together |
| **Parent completion** | a parent may not be `done` while a child is not, so if A depends on P, every descendant of P finishes before A becomes ready — with no direct A→child edge |
| **Both `done`** | a `done` item never writes again, so it cannot race anything |

Final classification: **0 live unserialized · 142 benign · 9 latent unserialized.**

### The 9 latent pairs — every pair that could collide if both became ready

| # | Pair | Shared path(s) | Assessment |
|---|---|---|---|
| 1 | ROOT.1 ↔ ROOT.7.2 | `package.json` | ROOT.7.2 is `done`; only reopening it revives this |
| 2 | ROOT.1.1 ↔ ROOT.7.2 | `package.json` | same |
| 3 | ROOT.1.1.4 ↔ ROOT.7.2 | `package.json`, `tests/bundle.test.ts` ~ `tests/**` | same |
| 4 | ROOT.1.10 ↔ ROOT.7.2 | `package.json`, `package-lock.json` | same |
| 5 | ROOT.1.5 ↔ ROOT.7.2 | `package.json` | same |
| 6 | **ROOT.2.1 ↔ ROOT.7.1** | `.program/interfaces/learning-events.md` ~ `.program/interfaces/**` | **genuine** — founding item vs steward |
| 7 | **ROOT.2.3 ↔ ROOT.7.1** | `.program/interfaces/judge-verdict.md` ~ `.program/interfaces/**` | **genuine** |
| 8 | **ROOT.4.5 ↔ ROOT.7.1** | `.program/interfaces/termevent-protocol.md` ~ `.program/interfaces/**` | **genuine** |
| 9 | **ROOT.4.8 ↔ ROOT.7.2** | `tests/**` ~ `tests/**` | **genuine** — two items with identical broad globs |

Pairs 1–5 are artifacts of ROOT.7.2 being `done` while its Phase-0 co-owners are not, and
are only hazardous if ROOT.7.2 is reopened. Note the review-quarantine question from
Phase 3 nearly made that happen: had the 13 `done` items gone back to `in_review`, five of
these would have become live. **Reopening a `done` item can create ownership collisions
that did not exist when it closed** — a reopen must re-run the overlap scan.

Pairs 6–8 are the same structural issue as the one fixed here, one phase later: ROOT.7.1's
`.program/interfaces/**` glob covers interface docs whose *founding* items have not run
yet. ADR-0007 #10 anticipated this ("interface docs get named-file protection via
ROOT.1.2/7.1 globs") but the protection is by convention, not by construction. Not fixed
now: those items are `proposed`, in later phases, and the correct remedy — the founding
item owns its doc until it closes, then the doc transfers — is the same
`file_ownership_deferred` pattern, best applied when each is decomposed. **Recorded so the
coordinator that decomposes ROOT.2 and ROOT.4 must handle it.**

Pair 9 is a real design defect: ROOT.4.8 and ROOT.7.2 both claim `tests/**` outright. They
are in different phases so nothing collides today, but the globs are indistinguishable and
neither is narrowed. **Flagged for ROOT.4 decomposition.**

## Consequence

- The invariant holds for the current active set, by construction rather than by assertion.
- `file_ownership_deferred` is available as the standard way to record a scheduled
  ownership transfer without asserting a present one.
- **A standing item cannot be serialized by `depends_on`.** Anything that never closes must
  instead hold the narrowest possible globs, and acquire paths only as they are genuinely
  released. This generalizes beyond ROOT.7.1 to any future standing service.
- The scan is reproducible: `.program/audits/ownership-overlap-scan/scan-globs.py`. It
  should be re-run at each phase boundary, whenever an item's globs change, and **before
  reopening any `done` item**.
- Auditor check 5 remains as-is (concurrently-active only) — but the latent set above is now
  written down, which is what check 5 structurally cannot give.

## If wrong

If two agents still collide on a shared path, check first whether one is a standing item
that reacquired a deferred glob early, and whether `file_ownership_deferred` was mistakenly
read as current ownership. If a `done` item is reopened, re-run the scan before dispatching
anything — pairs 1–5 become live immediately. If the scan itself is doubted, its overlap
test constructs a concrete witness path for every wildcard match, printed beside each hit,
so any claimed overlap can be checked by hand.
