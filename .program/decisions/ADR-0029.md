# ADR-0029: Ratification — REQ-CP-05 s3 rejection clause is falsifiable (standard shape)

Status: ratified 2026-07-28
Item: ROOT.7.3.11
Spec: content-pipeline.md REQ-CP-05 scenario 3

## Claim

REQ-CP-05 scenario 3's rejection clause — "any value outside an enumerated inside throws TypeError with JSON path" — is the standard falsifiable shape for a rejection obligation and requires no shard edit.

## Evidence

### 1. The spec text is checkably precise

CP-05 s3 (lines 92-93 in content-pipeline.md) states:
> Given item content containing a value outside the hash-input domain — including any value or structural condition NOT matched by the HASHABLE enumeration, a sparse-array hole, or nesting beyond MAX_HASH_DEPTH — when the hash is computed, then the computation fails with a `TypeError` naming the path of the offending value — it never silently coerces, collapses, or crashes with an unrelated error.

The "hash-input domain" is ENUMERATED (lines 66-87): null, booleans, finite numbers, strings, dense arrays, plain objects, MAX_HASH_DEPTH=64. The enumeration is CLOSED-WORLD per ADR-0017 Amendment 1 (line 68): "the HASHABLE list is exhaustive; there is no third category."

The rejection semantics are NAMED (lines 76-87): TypeError (NOT bare RangeError), with JSON path, for anything not matched by a HASHABLE rule. Specific examples are ILLUSTRATIVE, not definitional (line 77).

### 2. The implementation is checkable against the spec

The enforcement in `src/lib/revisions.ts` is structured as an allowlist (lines 375-421, `canonicalStringify`; lines 423-525, `canonicalStringifyContainer`):
- Each HASHABLE rule has one explicit case (boolean line 392, finite number 395-403, string 406, null 412, arrays 439-496, plain objects 498-517).
- The default branches THROW (line 419 primitive default, line 521 container fallthrough).
- Every rejection names the path via `rejectOutOfDomain(path, description)` (line 274-280).
- Cycle detection throws TypeError with path (line 431-434), never bare RangeError.

### 3. The test suite exercises the rejection clause repeatedly

`tests/revisions.test.ts` lines 164-323 ("CP-05 hash-input domain enforcement (scenario 3)") contains 24 rejection tests, each asserting:
- `instanceof TypeError` (line 173), NOT RangeError
- Path substring present in message (line 175)
- Descriptor regex match (line 176)

Examples that directly exercise the "outside an enumerated inside" clause:
- **undefined** (line 180): `(root)` path, `/undefined/` descriptor
- **function** (line 188): `verifier` path, `/function/`
- **symbol** (line 196): `tag` path, `/symbol/`
- **BigInt** (line 209): `count` path, `/BigInt/`
- **NaN** (line 214): `score` path, `/NaN/`
- **Date** (line 226): `meta.createdAt` path, `/Date/`
- **Map** (line 234): `lookup` path, `/Map/`
- **Set** (line 238): `skills` path, `/Set/`
- **RegExp** (line 242): `pattern` path, `/RegExp/`
- **Uint8Array** (line 246): `bytes` path, `/Uint8Array/`
- **class instance** (line 250-253): `rubric` path, `/Rubric/`
- **circular reference** (line 257-272): `beats[0].meta.parent` path, NOT RangeError, `/cycle/` descriptor
- **sparse-array hole** (ROOT.1.1.5 GEN2 defect cycle, verified against Amendment 1 A1.1)
- **nesting beyond MAX_HASH_DEPTH=64** (Amendment 1 A1.2, explicit depth counter)

### 4. The clause has survived adversarial review and defect cycles

The rejection clause's falsifiability was EXERCISED by:
- **GEN2 defect cycles** (ROOT.1.1.5): two classes of rejected values (non-plain arrays, array expando properties) were found SILENTLY ADMITTED by the gen1 implementation, contradicting the spec's rejection obligation. Both were FIXED by widening rejection (not by changing the spec), and 18 new tests were added proving the previously-silent cases now throw TypeError with path.
- **Adversarial review** (ROOT.1.1.4, tier-2 pair, both lenses approve/high): the hash-input domain enforcement survived spec-conformance review AFTER the GEN2 fixes landed, so the current spec text + implementation pair has been checked against each other.
- **Bundle version id freeze** (ROOT.1.1.5 AC3 hard invariant): all rejection-widening changes preserved the emitted bundle version id `eb647973722173b3` for the real authored corpus (74 arrays, 0 with a disallowed prototype/key/property), proving in-domain content hashes are stable.

### 5. Survey disposition agrees

The 2026-07-27 unfalsifiable-criteria survey (`.program/audits/2026-07-27T0540-unfalsifiable-criteria-survey.md`, line 29, CP-05 row in the "Borderline" table) ruled CP-05 s3 ACCEPTED AS-IS:
> new ADR-0017 scenario: rejected-domain is "outside" an enumerated inside — open only over future JS types

The director's disposition (lines 32-38) states:
> The CP-05 s3 borderline is accepted as-is: "outside an enumerated inside" is the standard shape of a rejection clause and is testable per named rejected type.

## Ruling

REQ-CP-05 s3's rejection clause conforms to the standard falsifiable shape:
- **Named rejected type**: TypeError (not RangeError, not silent coercion)
- **Named procedure**: the test suite's 24 rejection tests in `tests/revisions.test.ts` lines 164-323, plus the GEN2 defect cycle's 18 widening tests (ROOT.1.1.5)
- **Checkable against reality**: the implementation's allowlist structure (default branch throws) + the suite's `expectRejected` helper establish a two-way check (spec ↔ implementation)

The enumeration is CLOSED-WORLD per ADR-0017 Amendment 1 (A1.3), so "outside" is decidable: any value not explicitly matched by a HASHABLE rule is outside. The test obligation is NOT "one test per future JS type" (open, unfalsifiable) but "the default-reject branch has coverage proving an unlisted value throws with path" (closed, checkable) — satisfied by line 419 primitive default + line 521 container fallthrough, both exercised.

## Gaps found

ZERO. The spec text is precise enough to check, the implementation is checkable, and the test suite exercises the clause. No shard edit is required.

## Consequences

- REQ-CP-05 s3 requires no amendment for Phase 0 Gate.
- The "outside an enumerated inside" pattern is ratified as the standard falsifiable shape for rejection clauses; future enumeration passes (the 8 clear matches in the survey) should follow this template.
- No routing action: this was a ratification-only item, and no gap was found.
