# ADR-0023 — REQ-FP-04 s2 celebration trigger-point enumeration (closed-world)

Date: 2026-07-28. Author: implementer-ROOT.7.3.5-gen0.
Status: ratified.
Spec ref: .program/spec/frontend-platform.md#req-fp-04 scenario 2.

## Context

REQ-FP-04 s2 says "Given **any celebration anywhere**, when its trigger is traced, then it is a typed server-confirmed projection-transition event, never a client-side guess." The universal quantifier "any celebration anywhere" was unfalsifiable over an unenumerated domain (.program/audits/2026-07-27T0540-unfalsifiable-criteria-survey.md, row frontend-platform REQ-FP-04 s2): no test suite can cover an open set of trigger points, so the criterion could pass review while the guarantee was false for unnamed triggers.

Following the precedent established in ADR-0017 (CP-05 hash-input domain enumeration) and ADR-0019 (API-03 SSE-endpoint enumeration), this decision enumerates all celebration trigger points in the ai-learning-app closed-world, defines a per-trigger testable criterion, and establishes an additive relaxation path for new triggers.

## The enumerated celebration trigger domain (normative, exhaustive)

REQ-FP-04 s2 obligations apply to exactly SEVEN celebration trigger points:

### 1. First quiz pass (first-run moment)
- **Event type:** `quiz_passed` (first occurrence per profile lifetime)
- **Owning spec:** dashboard-and-wayfinding.md REQ-DW-05 ("First-run — no form, no lecture")
- **Owning item:** ROOT.2.1 (Dashboard & Wayfinding capability, Phase 1)
- **Projection field:** First quiz pass detected via SkillState projection (first clear positive evidence event per profile)
- **Celebration tier:** MICRO (120–180ms) — small, establishing that celebrations are earned server-confirmed events
- **Server-confirmed projection transition:** quiz_passed event → SkillState first evidence record created
- **Per-trigger testable criterion:** Given the learner's first quiz pass, when the server-confirmed quiz_passed event arrives with SkillState showing first evidence, then a micro-tier celebration fires; given any interaction before that first server-confirmed event, then zero celebrations have fired.

### 2. Lesson completion
- **Event type:** `lesson_completed`
- **Owning spec:** lesson-experience.md REQ-LX-05 ("Celebration interstitial on server-confirmed completion")
- **Owning item:** ROOT.2.2 (Lesson Experience capability, Phase 1)
- **Projection field:** ResumePosition.lessonStatus = Complete
- **Celebration tier:** MESO (250–400ms spring) — checkmark bloom, objectives recap, score recap, streak tick, next-lesson CTA
- **Server-confirmed projection transition:** lesson_completed event → ResumePosition.lessonStatus becomes Complete
- **Per-trigger testable criterion:** Given the final exercise of a lesson passing, when the server-confirmed lesson_completed event arrives and ResumePosition.lessonStatus transitions to Complete, then the lesson-completion interstitial renders with meso-tier celebration; before that event, no interstitial appears.

### 3. Module mastery
- **Event type:** `module_mastered`
- **Owning spec:** mastery-model.md REQ-MM-04 ("Module states with Mastered = MIN over skills")
- **Owning item:** ROOT.3.2 (Mastery Model capability, Phase 2)
- **Projection field:** Module state transitions to Mastered (MIN over skills Fluent AND boss passed)
- **Celebration tier:** MACRO (600–900ms) — lesson/module/mastery milestone tier per REQ-FP-04
- **Server-confirmed projection transition:** Final skill-fluency or boss-pass event → module state computation yields Mastered
- **Per-trigger testable criterion:** Given the event that causes a module's state to transition to Mastered (all skills Fluent, boss passed), when the server confirms the transition, then a macro-tier celebration fires; given a module state of Complete (not Mastered), then no mastery celebration occurs.

### 4. Boss challenge pass
- **Event type:** `boss_passed`
- **Owning spec:** boss-and-test-out.md REQ-BT-01 ("One boss per module gates Mastered, never Complete")
- **Owning item:** ROOT.3.3 (Boss & Test-Out capability, Phase 2)
- **Projection field:** Boss exercise status = passed (contributes to module Mastered state)
- **Celebration tier:** MESO (250–400ms spring) — integrative achievement, gates Mastered
- **Server-confirmed projection transition:** boss_passed event (gate-tier verdict) → boss status becomes passed
- **Per-trigger testable criterion:** Given a boss exercise passing its gate-tier verdict, when the server-confirmed boss_passed event arrives, then a meso-tier celebration fires; given a boss attempt that fails or scores in the judge-noise firewall band (0.4–0.7), then no celebration occurs.

### 5. Test-out full pass
- **Event type:** `test_out` (full pass variant)
- **Owning spec:** boss-and-test-out.md REQ-BT-02 ("Test-out ('Prove it') per module")
- **Owning item:** ROOT.3.3 (Boss & Test-Out capability, Phase 2)
- **Projection field:** Module lessons marked complete via test_out, skills seeded Practiced
- **Celebration tier:** MESO (250–400ms spring) — equivalent to lesson completion batch, no-stigma presentation
- **Server-confirmed projection transition:** test_out event (full pass) → module lessons become Complete, skills seeded
- **Per-trigger testable criterion:** Given a full test-out pass, when the server-confirmed test_out event marks lessons complete and seeds skills, then a meso-tier celebration fires; given a partial test-out, then no celebration fires (progress seeded silently per what was demonstrated).

### 6. Artifact created/verified (Workshop)
- **Event type:** `artifact_created`
- **Owning spec:** workshop-and-artifacts.md REQ-WA-04 ("Artifact shelf with live health badges")
- **Owning item:** ROOT.4.2 (Workshop & Artifacts capability, Phase 3)
- **Projection field:** ArtifactHealth projection gains new artifact record (status: healthy)
- **Celebration tier:** MESO (250–400ms spring) — shelf animation, accumulation-progress narrative per Sage
- **Server-confirmed projection transition:** artifact_created event (verifier pass) → ArtifactHealth projection shows new healthy artifact
- **Per-trigger testable criterion:** Given a new artifact verified (workshop exercise pass), when the server-confirmed artifact_created event arrives and ArtifactHealth shows the new artifact as healthy, then the shelf animation plays; given a verification in progress or failed, then no celebration occurs.

### 7. Streak milestone
- **Event type:** `streak_milestone` (emitted on milestone days: 7, 14, 30, 60, 90, 180, 365)
- **Owning spec:** frontend-platform.md REQ-FP-04 (macro tier explicitly names streak milestones)
- **Owning item:** ROOT.2.1 (Dashboard & Wayfinding capability, Phase 1)
- **Projection field:** Streak projection (active_days count)
- **Celebration tier:** MACRO (600–900ms) — streak milestone in the lesson/module/mastery tier
- **Server-confirmed projection transition:** session_started or review_completed event on a new calendar day → Streak.active_days crosses a milestone threshold
- **Per-trigger testable criterion:** Given a session or review that increments Streak.active_days to exactly a milestone value (7, 14, 30, 60, 90, 180, 365), when the server confirms the transition, then a macro-tier celebration fires; given Streak.active_days incrementing to a non-milestone value, then no streak celebration occurs.

## Closed-world rule

**The enumeration above is exhaustive.** Any celebration-like moment not on this list MUST NOT trigger confetti/macro-motion celebration animations until explicitly added by a future additive ADR. Creating a celebration trigger outside this list without amending this ADR first is a spec violation.

Celebration-like moments explicitly ruled OUT of the celebration domain:
- **Skill state transitions (Introduced → Practiced, Practiced → Fluent):** Mastery-model.md REQ-MM-02 states these are evidence-counted promotions with no celebration specified. Skills are the unit of mastery tracking, but their transitions are intermediate states; celebrations fire on composed milestones (module mastery, boss pass).
- **Review warm-up session completion:** Spaced-review.md REQ-SR-04 describes the warm-up UX ("~5-minute warm-up clears the visible queue") with no celebration specified. Warm-up is a maintenance activity; no milestone framing.
- **Individual exercise passes (non-boss quiz/playground/challenge):** Lesson-experience.md REQ-LX-02 describes per-type completion predicates (quizzes passed, challenges verified, playgrounds attempted) as inputs to lesson completion, not celebration moments themselves. The lesson completion interstitial (trigger #2) is the celebration boundary.
- **Repair success (Workshop regression fixed):** Workshop-and-artifacts.md REQ-WA-05 states repair emits positive debugging evidence but frames regression repair as non-punitive investigation ("this happens to every developer"), not a milestone. No celebration specified.
- **Frontend UI state changes (beat transitions, rail advances, Continue clicks):** These are navigation/pacing mechanics (lesson-experience.md REQ-LX-01), not server-confirmed projection transitions.
- **"Prove it" popover appearance (test-out offer):** Dashboard-and-wayfinding.md REQ-DW-02 and boss-and-test-out.md REQ-BT-02 describe the test-out affordance as a start option, not a celebration trigger. The test-out *full pass* (trigger #5) is the celebration boundary.
- **Profile creation, theme switch, keyboard nav:** Frontend-platform operations, not progression milestones.

## Relaxation path

To admit a new celebration trigger:
1. Write an additive ADR that:
   - Names the new trigger (event type, owning spec/item, projection field, celebration tier).
   - Defines the server-confirmed projection transition that authorizes the celebration.
   - States a per-trigger testable criterion in the form: "Given [precondition], when [server-confirmed event + projection transition], then [celebration tier] celebration fires; given [negative case], then no celebration occurs."
   - Confirms the trigger does not contradict CONSTRAINTS.md #12 [HARD] (non-competitive) or the "celebrations fire only on server-confirmed projection transitions" policy.
2. Amend frontend-platform.md additively to reference the new ADR.
3. Update this ADR's enumeration section by appending the new trigger entry.

## Cross-shard consistency check

**Lesson-experience.md REQ-LX-05 co-ownership verified:** The lesson-completion interstitial (trigger #2) is fully specified in lesson-experience.md with explicit dependency on frontend-platform.md REQ-FP-04 for the celebration ladder and server-confirmed-event policy. No divergence.

**Workshop-and-artifacts.md REQ-WA-04 co-ownership verified:** The artifact shelf animation (trigger #6) explicitly cites "server-confirmed, per frontend-platform REQ-FP-04" and states the trigger is the artifact_created event arriving. No divergence.

**Dashboard-and-wayfinding.md REQ-DW-05 co-ownership verified:** The first-run quiz celebration (trigger #1) is stated as "establishing that celebrations are earned, server-confirmed events" and frames it as a small celebration (matching micro tier). No divergence.

**Boss-and-test-out.md consistency verified:** REQ-BT-01 describes the boss as an integrative challenge gating Mastered; REQ-BT-02 describes test-out full pass as marking lessons complete with "identical presentation (no 'skipped' badge — no stigma)." Both are progression milestones consistent with meso-tier celebration. Boss unlimited retries and hint ladder availability (REQ-BT-01) mean failures do not punish; celebrations are reserved for success. No divergence.

**Mastery-model.md consistency verified:** REQ-MM-04 states module Mastered = MIN over skills (all Fluent) AND boss passed. The module-mastery celebration (trigger #3) fires on this composed state transition, not on individual skill transitions. REQ-MM-02 explicitly states "never demote" and frames failures as invisible scheduler resets, not celebration-worthy negative events. Consistent.

**Spaced-review.md consistency verified:** REQ-SR-04 describes warm-up as "~5-minute warm-up clears the visible queue" with "no debt framing." The absence of a warm-up completion celebration is consistent with the non-punitive, maintenance-activity framing. No contradiction.

**Constraints/REJECTED check:** CONSTRAINTS.md #12 [HARD] prohibits competitive framing; all enumerated triggers are intrinsic progression milestones, not comparisons. REJECTED.md lines 51–54 explicitly reject "XP / levels" and "leaderboards / social features" — none of the enumerated triggers are extrinsic rewards. No contradiction.

## Readings considered

- ADR-0017 (CP-05 hash-input domain): established the closed-world enumeration pattern ("the enumeration is exhaustive; everything outside it is rejected").
- ADR-0019 (API-03 SSE-endpoint domain): demonstrated per-trigger falsifiable criteria and relaxation path structure.
- ADR-0028 (MS-03 delete-verb domain): demonstrated baseline audit + exception recording patterns (not applicable here — no pre-existing celebration code exists to audit).
- Unfalsifiable-criteria survey row frontend-platform REQ-FP-04 s2: identified "any celebration anywhere" as a clear match (universal quantifier over unenumerated domain).
- frontend-platform.md REQ-FP-04: owns the celebration policy, motion tiers, and server-confirmed-event requirement.
- lesson-experience.md REQ-LX-05, workshop-and-artifacts.md REQ-WA-04, dashboard-and-wayfinding.md REQ-DW-05: the three shards that explicitly name celebration moments.
- mastery-model.md, boss-and-test-out.md, spaced-review.md: shards checked for implicit celebration moments or contradictions; none found.
- CONSTRAINTS.md #12 [HARD] (non-competitive), REJECTED.md (XP/badges/leaderboards rejected): no enumerated trigger violates these.

## Consequences

- frontend-platform.md REQ-FP-04 s2 amended additively to quantify over the enumerated triggers (domain clause added under s2).
- Acceptance tests for s2 are now per-trigger checks: each enumerated trigger must verify server-confirmed projection transition + correct celebration tier + negative-case silence.
- Creating a celebration trigger outside this list without an additive ADR is a spec violation (caught at review or by grep-based audit for confetti API calls).
- The unfalsifiable "any celebration anywhere" phrase is now bounded and testable.
- Celebration-like moments explicitly ruled OUT are recorded, so future proposals to celebrate them can cite this ADR and follow the relaxation path.
