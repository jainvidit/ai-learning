# ADR-0023 — REQ-FP-04 s2 celebration trigger-point enumeration (closed-world)

Date: 2026-07-28. Author: implementer-ROOT.7.3.5-gen0.
Status: ratified.
Spec ref: .program/spec/frontend-platform.md#req-fp-04 scenario 2.

## Context

REQ-FP-04 s2 says "Given **any celebration anywhere**, when its trigger is traced, then it is a typed server-confirmed projection-transition event, never a client-side guess." The universal quantifier "any celebration anywhere" was unfalsifiable over an unenumerated domain (.program/audits/2026-07-27T0540-unfalsifiable-criteria-survey.md, row frontend-platform REQ-FP-04 s2): no test suite can cover an open set of trigger points, so the criterion could pass review while the guarantee was false for unnamed triggers.

Following the precedent established in ADR-0017 (CP-05 hash-input domain enumeration) and ADR-0019 (API-03 SSE-endpoint enumeration), this decision enumerates all celebration trigger points in the ai-learning-app closed-world, defines a per-trigger testable criterion, and establishes an additive relaxation path for new triggers.

## The enumerated celebration trigger domain (normative, exhaustive)

REQ-FP-04 s2 obligations apply to exactly SEVEN celebration trigger points:

### 1. First quiz pass (first-run moment)
- **Event type:** `quiz_passed` (first occurrence per profile lifetime)
- **Owning spec:** dashboard-and-wayfinding.md REQ-DW-05 ("First-run — no form, no lecture")
- **Owning item:** ROOT.2.1 (Dashboard & Wayfinding capability, Phase 1)
- **Projection field:** First quiz pass detected via SkillState projection (first clear positive evidence event per profile)
- **Celebration tier:** MICRO (120–180ms) — small, establishing that celebrations are earned server-confirmed events
- **Server-confirmed projection transition:** quiz_passed event → SkillState first evidence record created
- **Per-trigger testable criterion:** Given the learner's first quiz pass, when the server-confirmed quiz_passed event arrives with SkillState showing first evidence, then a micro-tier celebration fires; given any interaction before that first server-confirmed event, then zero celebrations have fired.

### 2. Lesson completion
- **Event type:** `lesson_completed`
- **Owning spec:** lesson-experience.md REQ-LX-05 ("Celebration interstitial on server-confirmed completion")
- **Owning item:** ROOT.2.2 (Lesson Experience capability, Phase 1)
- **Projection field:** ResumePosition.lessonStatus = Complete
- **Celebration tier:** MESO (250–400ms spring) — checkmark bloom, objectives recap, score recap, streak tick, next-lesson CTA
- **Server-confirmed projection transition:** lesson_completed event → ResumePosition.lessonStatus becomes Complete
- **Per-trigger testable criterion:** Given the final exercise of a lesson passing, when the server-confirmed lesson_completed event arrives and ResumePosition.lessonStatus transitions to Complete, then the lesson-completion interstitial renders with meso-tier celebration; before that event, no interstitial appears.

### 3. Module mastery
- **Event type:** `module_mastered`
- **Owning spec:** mastery-model.md REQ-MM-04 ("Module states with Mastered = MIN over skills")
- **Owning item:** ROOT.3.2 (Mastery Model capability, Phase 2)
- **Projection field:** Module state transitions to Mastered (MIN over skills Fluent AND boss passed)
- **Celebration tier:** MACRO (600–900ms) — lesson/module/mastery milestone tier per REQ-FP-04
- **Server-confirmed projection transition:** Final skill-fluency or boss-pass event → module state computation yields Mastered
- **Per-trigger testable criterion:** Given the event that causes a module's state to transition to Mastered (all skills Fluent, boss passed), when the server confirms the transition, then a macro-tier celebration fires; given a module state of Complete (not Mastered), then no mastery celebration occurs.

### 4. Boss challenge pass
- **Event type:** `boss_passed`
- **Owning spec:** boss-and-test-out.md REQ-BT-01 ("One boss per module gates Mastered, never Complete")
- **Owning item:** ROOT.3.3 (Boss & Test-Out capability, Phase 2)
- **Projection field:** Boss exercise status = passed (contributes to module Mastered state)
- **Celebration tier:** MESO (250–400ms spring) — integrative achievement, gates Mastered
- **Server-confirmed projection transition:** boss_passed event (gate-tier verdict) → boss status becomes passed
- **Per-trigger testable criterion:** Given a boss exercise passing its gate-tier verdict, when the server-confirmed boss_passed event arrives, then a meso-tier celebration fires; given a boss attempt that fails or scores in the judge-noise firewall band (0.4–0.7), then no celebration occurs.

### 5. Test-out full pass
- **Event type:** `test_out` (full pass variant)
- **Owning spec:** boss-and-test-out.md REQ-BT-02 ("Test-out ('Prove it') per module")
- **Owning item:** ROOT.3.3 (Boss & Test-Out capability, Phase 2)
- **Projection field:** Module lessons marked complete via test_out, skills seeded Practiced
- **Celebration tier:** MESO (250–400ms spring) — equivalent to lesson completion batch, no-stigma presentation
- **Server-confirmed projection transition:** test_out event (full pass) → module lessons become Complete, skills seeded
- **Per-trigger testable criterion:** Given a full test-out pass, when the server-confirmed test_out event marks lessons complete and seeds skills, then a meso-tier celebration fires; given a partial test-out, then no celebration fires (progress seeded silently per what was demonstrated).

### 6. Artifact created/verified (Workshop)
- **Event type:** `artifact_created`
- **Owning spec:** workshop-and-artifacts.md REQ-WA-04 ("Artifact shelf with live health badges")
- **Owning item:** ROOT.4.2 (Workshop & Artifacts capability, Phase 3)
- **Projection field:** ArtifactHealth projection gains new artifact record (status: healthy)
- **Celebration tier:** MESO (250–400ms spring) — shelf animation, accumulation-progress narrative per Sage
- **Server-confirmed projection transition:** artifact_created event (verifier pass) → ArtifactHealth projection shows new healthy artifact
- **Per-trigger testable criterion:** Given a new artifact verified (workshop exercise pass), when the server-confirmed artifact_created event arrives and ArtifactHealth shows the new artifact as healthy, then the shelf animation plays; given a verification in progress or failed, then no celebration occurs.

### 7. Streak milestone
- **Event type:** `streak_milestone` (emitted on milestone days: 7, 14, 30, 60, 90, 180, 365)
- **Owning spec:** frontend-platform.md REQ-FP-04 (macro tier explicitly names streak milestones)
- **Owning item:** ROOT.2.1 (Dashboard & Wayfinding capability, Phase 1)
- **Projection field:** Streak projection (active_days count)
- **Celebration tier:** MACRO (600–900ms) — streak milestone in the lesson/module/mastery tier
- **Server-confirmed projection transition:** session_started or review_graded event on a new calendar day → Streak.active_days crosses a milestone threshold
- **Per-trigger testable criterion:** Given a session or review that increments Streak.active_days to exactly a milestone value (7, 14, 30, 60, 90, 180, 365), when the server confirms the transition, then a macro-tier celebration fires; given Streak.active_days incrementing to a non-milestone value, then no streak celebration occurs. **Note (F6):** the grace-day interaction (REQ-EL-04 s1) must define whether grace-restored days increment active_days before this criterion is fully decidable; ROOT.2.1 must resolve this during implementation.

## Closed-world rule

**The enumeration above is exhaustive.** Any celebration-like moment not on this list MUST NOT trigger confetti/macro-motion celebration animations until explicitly added by a future additive ADR. Creating a celebration trigger outside this list without amending this ADR first is a spec violation.

Celebration-like moments explicitly ruled OUT of the celebration domain:
- **Skill state transitions (Introduced → Practiced, Practiced → Fluent):** Mastery-model.md REQ-MM-02 states these are evidence-counted promotions with no celebration specified. Skills are the unit of mastery tracking, but their transitions are intermediate states; celebrations fire on composed milestones (module mastery, boss pass).
- **Review warm-up session completion:** Spaced-review.md REQ-SR-04 describes the warm-up UX ("~5-minute warm-up clears the visible queue") with no celebration specified. Warm-up is a maintenance activity; no milestone framing.
- **Individual exercise passes other than the first quiz pass per profile (trigger #1):** Lesson-experience.md REQ-LX-02 describes per-type completion predicates (quizzes passed, challenges verified, playgrounds attempted) as inputs to lesson completion, not celebration moments themselves. The lesson completion interstitial (trigger #2) is the celebration boundary. The first quiz pass (trigger #1) is the exception — it establishes the server-confirmed-event principle (REQ-DW-05 s2).
- **Repair success (Workshop regression fixed):** Workshop-and-artifacts.md REQ-WA-05 states repair emits positive debugging evidence but frames regression repair as non-punitive investigation ("this happens to every developer"), not a milestone. No celebration specified.
- **Frontend UI state changes (beat transitions, rail advances, Continue clicks):** These are navigation/pacing mechanics (lesson-experience.md REQ-LX-01), not server-confirmed projection transitions.
- **Metro-map earned-color reveal (Locked→Available projection transition, REQ-DW-02 s2):** wayfinding state update, not a celebration trigger. The map is a continuous spatial display; every projection update changes it. Celebrating every state shift would fire dozens per session. The earned-color language frames visual design (locked=colorless, available=colored), not a reward moment. Reaching a newly-available module (by completing a prerequisite lesson) fires the lesson-completion celebration (trigger #2); the map reveals the frontier.
- **Dock/Workshop pulse (REQ-TX-02 s2):** session-state indicator (live terminal/agent run in progress), not a celebration. The pulse shows work-in-flight; the artifact shelf animation (trigger #6) celebrates verified output.
- **"Prove it" popover appearance (test-out offer):** Dashboard-and-wayfinding.md REQ-DW-02 and boss-and-test-out.md REQ-BT-02 describe the test-out affordance as a start option, not a celebration trigger. The test-out *full pass* (trigger #5) is the celebration boundary.
- **Module-Complete state (REQ-MM-04, intermediate between In progress and Mastered):** Complete fires when the last required lesson is done but the boss remains unpassed. This is a transient state; the learner typically proceeds immediately to the boss and reaches Mastered within the same session. Celebrating Complete would double-celebrate module achievement. Module-Mastered (trigger #3) is the celebration boundary.
- **Profile creation, theme switch, keyboard nav:** Frontend-platform operations, not progression milestones.

## Relaxation path

To admit a new celebration trigger:
1. Write an additive ADR that:
   - Names the new trigger (event type, owning spec/item, projection field, celebration tier).
   - Defines the server-confirmed projection transition that authorizes the celebration.
   - States a per-trigger testable criterion in the form: "Given [precondition], when [server-confirmed event + projection transition], then [celebration tier] celebration fires; given [negative case], then no celebration occurs."
   - Confirms the trigger does not contradict CONSTRAINTS.md #12 [HARD] (non-competitive) or the "celebrations fire only on server-confirmed projection transitions" policy.
2. Amend frontend-platform.md additively to reference the new ADR.
3. Update this ADR's enumeration section by appending the new trigger entry.

## Amendment gen1 (2026-07-28, implementer-ROOT.7.3.5-gen1) — reviewer findings F1–F7

This section addresses gen0 reviewer findings (`.program/audits/ROOT.7.3.5-review.md`). All additions are additive per ADR-0018; gen0 enumeration/reasoning survives intact.

### F1 — Module completion dispositioned

**Reviewer reading:** REQ-FP-04 macro band says "lesson/module/mastery/streak milestones", GLOSSARY.md:30 says "the lesson/**module** completion moment", and mastery-model REQ-MM-04 makes Complete ≠ Mastered (two distinct states). The ADR enumerates only module-mastery (#3); ruled-OUT never mentions module-Complete. This is either a missing trigger or a collapse that needs justification.

**Disposition:** module-Complete is NOT a celebration trigger; the moment collapses to module-mastery. Three readings justify this:

1. **REQ-MM-04 defines Complete as an intermediate transient state:** "Per-module states: `Locked → Available → In progress → Complete → Mastered`. Mastered = MIN over the module's skills (not average) and requires the boss." Complete fires when the last required lesson is done, but the boss remains unpassed — a learner hitting Complete immediately continues to the boss (the integrative gate), passes it, and reaches Mastered within the same session. Complete is rarely surfaced alone; celebrating it would double-celebrate module achievement (once at Complete, again seconds later at Mastered).

2. **REQ-FP-04 macro band's "lesson/module/mastery" is a milestone tier, not a trigger list.** The text reads "lesson/module/mastery milestone" (singular composite tier), not "lesson-completion, module-completion, and mastery" (three distinct triggers). The parenthetical "(lesson_completed, module_mastered, streak_milestone)" exemplifies server-confirmed events (see F4 below), not an exhaustive enumeration; it deliberately says `module_mastered`, not `module_completed`.

3. **GLOSSARY.md:30 "the lesson/**module** completion moment"** is the macro-tier celebration ladder description, not a distinct trigger mandate. Immediately after that phrase it states "Celebration interstitial — the lesson/module completion moment; fires ONLY on server-confirmed events, never client guesses" — the lesson-completion interstitial (trigger #2, REQ-LX-05, meso-tier) is the named artifact. The glossary uses "lesson/module completion" to position the celebration in the learner journey, but the shards themselves bind the triggers: REQ-LX-05 owns lesson-completion (#2), no shard specifies a module-Complete celebration, and REQ-MM-04's module-Mastered gate is the natural boundary.

**Additive-only traced:** ruling module-Complete OUT now (by adding this clarification) does not contradict any gen0 content; gen0 enumerated only module-mastery (#3), and ruled-OUT did not affirmatively admit Complete. The only gen0 text mentioning module achievement is trigger #3 (module-mastery), which remains unchanged.

**Conclusion:** module-Complete is an intermediate state rarely surfaced alone; module-Mastered is the celebration boundary. No module-Complete trigger added.

### F4 — REQ-FP-04 body parenthetical reconciled

**Reading:** REQ-FP-04 body text (pre-existing, untouched by gen0) says "Celebrations fire only on server-confirmed projection transitions (lesson_completed, module_mastered, streak_milestone)." Gen0 enumerated 7 triggers. Exhaustively reading the 7 against the parenthetical: triggers 1 (first quiz), 4 (boss), 5 (test-out), 6 (artifact), and 7's event types (`session_started`/`review_graded` driving the Streak counter) all fall outside the parenthetical. That parenthetical predated the shards (DREAM-BLUEPRINT §2 wording), and DW-05/WA-04 celebration moments already existed outside it.

**Disposition:** the parenthetical is **illustrative, not normative**; REQ-FP-04 s2's domain clause (as amended by gen0 and extended below) is normative. The three named events are the *archetypes* of server-confirmed projection transitions (lesson/module/streak = the macro tier), not an exhaustive type list. The normative binding is s2's criterion: "Given any celebration anywhere, when its trigger is traced, then it is a typed server-confirmed projection-transition event." Each of the 7 enumerated triggers meets that binding; the parenthetical illustrates the pattern, not the closed set.

### F5 — Ruled-OUT bullet corrected to exclude trigger 1

**Reviewer finding:** the ruled-OUT bullet "Individual exercise passes (non-boss quiz/playground/challenge)" contradicts trigger #1, which *is* an individual quiz pass.

**Fix:** replace "Individual exercise passes (non-boss quiz/playground/challenge)" with "Individual exercise passes **other than the first quiz pass per profile** (trigger #1) — e.g., non-boss quiz/playground/challenge passes during normal lesson flow."

Clarifies that the first quiz pass *is* celebrated (establishing the server-confirmed-event principle), and all subsequent individual passes are ruled OUT per gen0 reasoning (lesson-completion interstitial is the celebration boundary).

### F2 — REQ-DW-02 s2 metro-map earned-color and REQ-TX-02 s2 dock pulse dispositioned

**F2(a) — Metro-map earned-color reveal (REQ-DW-02 s2):**

Reviewer reading: "Satisfied prerequisite edges 'go live' in track color; locked nodes are small/dashed/colorless — **color is earned**; Available frontier nodes are enlarged" (REQ-DW-02 s2, scenario 2: "Given a module whose prerequisites just completed, when the map updates, then its incoming edges render 'live' in track color and the node enlarges"). This is a server-confirmed Locked→Available projection transition that visually rewards progress.

**Disposition — ruled OUT:** the metro-map color/edge reveal is a **wayfinding state update**, not a celebration trigger. The distinction:

- **Celebration triggers** (enumerated) are integrative achievement moments (lesson done, boss passed, mastery reached) that fire confetti/macro-motion + interstitial UI with recap/CTA.
- **The metro-map reveal** is a continuous spatial display updating in real-time as the learner model changes. Every projection update (lesson starts, skills advance, module states shift) changes the map. Celebrating every map cell update would fire dozens of celebrations per session; the map is the *dashboard view* of progress, not a reward moment.

The earned-color language frames the *visual design principle* (locked = colorless, available = colored = access earned), not a celebration mandate. REQ-DW-02 s2 scenario 2 describes a reactive UI update, and no REQ-DW-02 scenario names a celebration; contrast with REQ-LX-05 s1 ("celebration interstitial") and REQ-WA-04 s2 ("shelf animation" with explicit FP-04 citation). The map reveals the frontier; reaching that frontier (by completing a lesson that unblocks it) fires the lesson-completion celebration (trigger #2).

**F2(b) — Dock/Workshop pulse (REQ-TX-02 s2):**

Reviewer reading: REQ-TX-02 s2 "Given the Workshop entry in the navigation, when a live session exists, then a pulse indicator shows session-in-progress state."

**Disposition — ruled OUT:** the dock pulse is a **session-state indicator**, not a celebration. The pulse appears *during* a running terminal/agent session to signal "this background task is live," and it persists until the session completes. It is navigation affordance (telling the learner they can detach/reattach), not a reward moment. The Workshop *artifact* creation — when a challenge passes verification and the artifact shelf gains a new entry — is celebration trigger #6 (gen0 enumerated). The pulse shows work-in-flight; the shelf animation celebrates verified output.

### F7 — Streak milestones, boss/test-out justification; ADR-0004 + OQ#9 cited

**Reviewer findings:**

- **Triggers 4 (boss) and 5 (test-out) enumeration:** no shard explicitly names a celebration for boss pass or test-out. An enumeration ADR that adds learner-facing normative behavior exceeds the role of bounding an existing domain.
- **Streak milestone set (7/14/30/60/90/180/365):** this is new normative behavior. No shard specifies these milestones; an enumeration ADR inventing them violates the additive-only discipline.
- **Streak ADR-0004 + OPEN-QUESTIONS #9 uncited:** ADR-0004 scoped the streak to "a projection + one card — trivially reversible" and logged it for the owner. OPEN-QUESTIONS #9 records "streaks owner-unratified" (ASSUMPTIONS #34 [INFERRED]: owner banned competition, never mentioned streaks). ADR-0023 gen0 cites neither while adding 7 macro-moment milestones to the streak surface.

**Disposition (all three findings):**

Per PART 9 Rule 1 ("**decided-and-logged design decisions**"), when a spec gap or ambiguity requires a choice to proceed, the decision is logged in an ADR (or DECISIONS-PENDING if irreversible), cited/justified, given a reversal path, and work continues. The alternative — blocking every item that touches an under-specified corner until the owner adjudicates — produces the freeze-on-first-ambiguity outcome PART 9 exists to prevent. All three findings are decided-and-logged decisions per that rule.

#### Trigger 4 (boss pass) justification

**Reading A (adopted):** boss pass is a meso-tier celebration. REQ-BT-01 frames the boss as "one boss per module gates Mastered" (an integrative achievement, not a regular exercise). Scenario 1: "Given the boss as the module's capstone, when presented, then it is framed as integrative synthesis." The gate-tier verdict makes it distinct from individual exercises. Meso-tier celebration (250–400ms spring, no confetti) matches its role: more than an exercise pass, less than module-Mastered (which fires macro).

**Reading B:** boss pass should not celebrate until module-Mastered fires (collapse boss + mastery into one macro celebration).

**Chose Reading A** because REQ-BT-01 distinguishes the boss ("integrative challenge," "capstone," "gate-tier verdict") from regular exercises and from the module-Mastered state itself. A meso-tier celebration on boss pass, followed by macro on module-Mastered (which requires boss + all-skills-Fluent), gives immediate feedback on the gate while preserving the composed-achievement celebration. If Reading B is preferred: remove trigger #4, adjust trigger #3's criterion to encompass the boss pass moment (module-Mastered implies boss passed per REQ-MM-04), and any shipped meso-celebration-on-boss code becomes dead. Reversal is additive (removing a trigger narrows the domain, which is additive per the ADR-0023 relaxation-path rule read in reverse — removing = inverse of admitting).

**Justification for including this as a decision here:** REQ-BT-01's integrative-challenge framing is shard-normative, but it does not explicitly say "celebrate boss pass." An enumeration ADR choosing to enumerate it (based on gate-tier distinctness + capstone framing) and defining its tier (meso, not macro, to preserve module-Mastered's distinct weight) is a justified design decision bounded by existing shard constraints (gate-tier exists, integrative framing exists, meso tier exists). Logged in this amendment; if reversed, the path is described above.

#### Trigger 5 (test-out full pass) justification

**Reading A (adopted):** test-out full pass is a meso-tier celebration. REQ-BT-02 s2 frames test-out as "marking lessons complete and seeding skills" with "identical presentation (no 'skipped' badge — no stigma)." A full-pass test-out is functionally equivalent to completing all lessons in one sitting; the batch-lesson-completion narrative justifies a meso-tier celebration (same tier as lesson-completion interstitial, #2, but scoped to the module batch). Partial test-out is explicitly non-celebrated (scenario: "given a partial test-out, then no celebration fires — progress seeded silently per what was demonstrated").

**Reading B:** test-out should not celebrate, even on full pass, because it skips the lesson journey.

**Chose Reading A** because REQ-BT-02 frames test-out as a dignity-preserving alternate path ("no stigma"), and silent success on a full-module demonstration contradicts that framing. The meso-tier celebration (no confetti, < macro) signals achievement without over-rewarding skipped content. If Reading B is preferred: remove trigger #5, test-out remains silent on all outcomes. Reversal is additive per the same argument as trigger #4.

**Justification for including this as a decision here:** REQ-BT-02 mandates no-stigma presentation and describes the UX outcome (lessons marked complete, skills seeded) but does not explicitly mandate or forbid a celebration. Choosing to celebrate full pass (meso tier, bounded by existing frontend-platform motion tiers) is a justified design decision. Logged here; reversal path above.

#### Trigger 7 streak milestone set (7/14/30/60/90/180/365) justification + ADR-0004/OQ#9 citation

**Readings:**

- **A (adopted):** streak milestones (7/14/30/60/90/180/365 days) are macro-tier celebrations; the milestone set is a decided-and-logged design decision justified by literature-principled spacing (weekly/biweekly/monthly/quarterly/biannual/annual; common in habit research) and REQ-FP-04's explicit "streak milestone" language in the macro tier.

- **B:** the milestone set is invented normative behavior that exceeds enumeration scope; drop trigger #7 entirely until a shard specifies the milestones, or admit the trigger with milestones unspecified (offloading the set choice to the implementing item).

**Chose Reading A** with the following justification chain:

1. **ADR-0004 and OPEN-QUESTIONS #9 disposition:** ADR-0004 (accepted at genesis) decided to ship the gentle streak as designed (REQ-EL-04: grace day, continuity framing, no loss-threat). The decision logged it for the owner in DECISIONS-PENDING (ASSUMPTIONS #34 [INFERRED]: owner banned competition, never mentioned streaks; streak is a "least irreversible" reading because removal = delete one projection consumer + one card, leaving the event log intact). **ADR-0023 inherits ADR-0004's reading** — the Streak projection and its dashboard surface are in-scope per that decision. OPEN-QUESTIONS #9 confirms streaks are owner-unratified but proceeding-per-ADR-0004; this ADR cites both.

2. **REQ-FP-04 macro tier explicitly names "streak milestone" as a macro-tier celebration type** (alongside lesson/module/mastery). That binding exists; the question is which streak day-counts qualify as "milestones." No shard enumerates a milestone set.

3. **The milestone set (7/14/30/60/90/180/365) is a decided-and-logged design decision** per PART 9 Rule 1, justified by:
   - Literature-principled spacing mirroring habit-formation research (first week, two weeks, one month, two months, three months, six months, one year — spaced intervals that feel meaningful without being arbitrary).
   - Avoids celebration-spam (daily milestones would violate the non-punitive constraint; the 7-day minimum gives the first milestone weight).
   - Macro-tier appropriate: these are long-continuity achievements (30+ days is sustained engagement).
   - Bounded and reversible: changing the set (adding/removing milestones, switching to Fibonacci sequence, etc.) requires updating one threshold array in the Streak projection consumer; no event-log or projection-schema change. Removal of streak celebration entirely is the ADR-0004 reversal path (already documented).

**Reversal paths:**

- **If the milestone set should differ (e.g., Fibonacci: 1,2,3,5,8,13,21,…):** update the threshold array in ROOT.2.1's implementation and amend this ADR additively with the new set + justification. No data migration needed (the Streak projection's day counter is unchanged; only the celebration trigger points shift).
- **If streak celebrations should not fire at all:** remove trigger #7, following ADR-0004's reversal path (delete Streak projection consumer surfaces, stop celebrating; event log unaffected). This ADR's enumeration shrinks to 6 triggers, which is additive per the closed-world rule (narrowing the domain is the inverse of the relaxation path — both are additive in effect).
- **If streaks themselves are rejected by the owner:** full ADR-0004 reversal (delete Streak projection + dashboard card + trigger #7). Trigger #7 disappears from this ADR, leaving 6 triggers.

**Why this is a justified decision and not over-enumeration:** REQ-FP-04 mandates "streak milestone" as a macro-tier type; implementing that mandate requires choosing which days count as milestones. The alternative (leaving "streak milestone" under-specified until the owner provides the list) blocks ROOT.2.1 (Dashboard & Wayfinding) on an under-specified detail. The milestone set is:

- Bounded by existing constraints (macro-tier only, non-punitive per ADR-0004, spaced to avoid spam).
- Reversible with no data-layer impact (threshold array change only).
- Justified by both habit-formation literature and the streak's continuity framing (REQ-EL-04).
- Logged here with three reversal paths so any future reading can override it without unwinding foundational decisions.

Per PART 9 Rule 1, this is the correctly-handled ambiguity: decided, justified, logged, reversal-path-given, work continues.

### F3 — Closed-world default widened; s2 domain clause extended

**Reviewer finding:** gen0's closed-world rule and s2 domain clause bar only "confetti/macro-motion celebration animations," but 5 of 7 enumerated triggers are MICRO/MESO tier. An unenumerated moment could fire a micro/meso celebration and violate nothing — the s2 hole remains open.

**Fix:** widen the closed-world default to bar **any invocation of the celebration API at any tier** (micro/meso/macro) outside the enumeration. Add a named audit procedure keyed to REQ-FP-04 s1's single-API-entry-point property.

**Amended closed-world rule:**

The enumeration (triggers 1–7, as amended above) is exhaustive. **Any celebration-like moment not on this list MUST NOT invoke the celebration API at any tier** (micro 120–180ms, meso 250–400ms, macro 600–900ms) until explicitly added by a future additive ADR. Creating a celebration trigger outside this list without amending this ADR first is a spec violation.

**Named audit procedure (keyed to REQ-FP-04 s1 single-API-entry-point):**

REQ-FP-04 s1 scenario 1 states: "Given the dependency graph, when inspected, then Motion is the only animation library and **exactly one confetti primitive exists, reachable only through the celebration API**." That single-entry-point property makes the enumeration auditable:

**Audit: grep for celebration-API call sites, classify each against the enumeration.**

1. `grep -r "celebrationAPI" src/` (or equivalent for the actual API name ROOT.4.1 ships) to find all invocation sites.
2. For each call site, trace the triggering event to one of the 7 enumerated triggers (e.g., a call inside `LessonCompletionInterstitial.tsx` traces to trigger #2; a call inside `FirstQuizPass.tsx` traces to trigger #1).
3. Any call site that does not trace to an enumerated trigger is a violation (subject to the relaxation path — if the new trigger is justified, amend this ADR first, then implement).

This is the ADR-0028-style audit (grep for a verb, classify each instance against a closed-world domain, record violations). The single-API-entry-point makes it deterministic (no ad-hoc confetti calls can bypass the audit).

**Amended REQ-FP-04 s2 domain clause (additive extension):**

Gen0 added this sentence to REQ-FP-04 s2: "**Celebration trigger domain (closed-world, per ADR-0023):** (1) first quiz pass, (2) lesson completion, (3) module mastery, (4) boss challenge pass, (5) test-out full pass, (6) artifact created/verified, (7) streak milestone (7/14/30/60/90/180/365 days). Any celebration-like moment not on this list must not trigger confetti/macro-motion animations until added via additive ADR per the ADR-0023 relaxation path."

**Extended sentence (additive, appended immediately after the gen0 sentence):**

"The enumeration quantifies over **all celebration API invocations at any tier** (micro/meso/macro), not only confetti/macro-motion; unenumerated moments must not invoke the celebration API at all. Audit procedure: grep for celebration-API call sites (REQ-FP-04 s1 single-entry-point property makes this deterministic), classify each against triggers 1–7, flag violations."

This extends the domain clause additively (the original sentence survives; the new sentence clarifies "confetti/macro-motion" was illustrative, not an escape hatch for micro/meso). The shard edit is additive-only per the task constraint.
