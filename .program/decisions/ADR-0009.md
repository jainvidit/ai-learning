# ADR-0009 — ASSUMPTIONS #11 discharged divergent: next-mdx-remote is no longer archived

**Status:** accepted (autonomous, PART 9 Rule 1)
**Item:** ROOT.1.7 (Probe), evidence `.program/audits/probes-mdx-archival.md`
**Date:** 2026-07-25

## Finding

The probe re-verified ASSUMPTIONS #11 and found the assumption no longer holds:
next-mdx-remote v6.0.0, last registry modification 2026-02-12, no deprecation flag,
4 active maintainers, repository hashicorp/next-mdx-remote. Independently confirmed by
the tier-0 fresh-eyes verifier re-running `npm view`.

## The two readings

1. **Reopen the pipeline choice** — the archival risk that motivated REQ-CP-01's Velite
   migration is gone, so keeping next-mdx-remote is viable again.
2. **Proceed as specified** — REQ-CP-01 requires next-mdx-remote absent and build-time
   compilation; REJECTED.md records the runtime-MDX approach as rejected on grounds
   beyond archival (build-time compilation to ordered beat arrays, REQ-CP-02, is a
   structural requirement archival status does not touch).

## Decision

Reading 2. The spec shard is binding, REJECTED.md is binding, and a decomposition that
reopens a rejected alternative is wrong by charter. Reading 2 is also the
least-irreversible: Velite migration proceeds; if the owner later prefers reading 1,
nothing destroyed the next-mdx-remote option beyond a package removal that git history
preserves.

## Consequences

- ROOT.1.1 proceeds with the Velite migration unchanged. Its coordinator holds the
  OQ #10 tiebreak (Velite two-process DX) and should weigh this evidence there: the
  fallback runner-up is healthier than the origin docs assumed, which LOWERS the risk of
  the tiebreak in either direction.
- ASSUMPTIONS #11 must not be cited as live justification in any future ADR.
- Logged to DECISIONS-PENDING.md for owner visibility; not blocking.
