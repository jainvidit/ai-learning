# ADR-0014 — The reviewer/auditor read-only guarantee: never enforced, now narrowed

**Status:** accepted (2026-07-26), amended 2026-07-27 (enforcement implemented; heartbeat
added, verified in fresh sessions) ·
**Companion to:** ADR-0013 (`memory:` ban) ·
**Enforcement:** PreToolUse hook keyed on `agent_type` —
`.claude/hooks/role-write-scope.py` via `.claude/hooks/run-hook.cmd` ·
**Inputs:** 125 subagent transcripts under
`.claude/projects/C--Users-jainv-workplace-ai-learning-app/*/subagents/agent-*.jsonl`,
role files in `.program/roles/`

## Context

Five roles — `dream-reviewer-primary`, `-secondary`, `-adversarial`,
`dream-ledger-auditor`, `-deep` — describe themselves as READ-ONLY, in the frontmatter
`description:` and again in a "Hard stops: read-only — you have no Write, Edit or Agent
tool and must not attempt to obtain one" line in the body.

Two separate things were wrong with that claim.

1. Write and Edit **were** present, silently granted by `memory: project` (ADR-0013).
   That is fixed.
2. Even with Write and Edit gone, **the guarantee still does not hold**, because all five
   roles have Bash. `npm test > somefile.txt`, `mkdir -p`, `mv`, `rm`, `tee`, a heredoc
   into any path — Bash writes anywhere the OS user can write. A tools allowlist that
   omits Write and Edit while including Bash does not produce a read-only agent, and never
   did.

## Decision

**The read-only guarantee was never enforced by the tools list, and a tools list cannot
enforce it. It is narrowed to a path constraint and moved to the permission layer.**

### Reviewers keep Bash. Deliberately.

This is not an oversight left in place for convenience. PART 6 of the operating prompt
requires empirical verification: a reviewer that cannot run `npm test`, `npx tsc
--noEmit`, or `npm run lint` cannot independently confirm anything and is reduced to
reading the implementer's own claims about its own work — exactly the failure mode blind
review exists to prevent. Framework-API claims in particular are only settleable by
running code, because this Next.js version diverges from training data (AGENTS.md). The
reviewers' value comes from re-running the evidence themselves. Removing Bash would buy a
guarantee nobody needs at the cost of the only thing that makes a review credible.

### The narrowed guarantee

> **Reviewers and auditors may write only under `.program/audits/**`.**

Everything else is out of bounds: artifacts under review, ledger item files, ledger event
files, `src/**`, `tests/**`, `content/**`, git, and role files.

Rationale for allowing that one path: reviewers legitimately need somewhere to put
verification output. The single Bash-write pattern observed in 38 generations was exactly
this — `dream-reviewer-primary` on ROOT.1.1.3 captured four command outputs to
`.program/audits/ROOT.1.1.3-verification/reviewer-*.txt`, namespaced under a `reviewer-`
prefix that cannot collide with the implementer's own evidence files, and not cited by any
`verification:` block as if it were the implementer's. That is a reviewer strengthening
its own verdict with independently produced evidence. It is the behaviour we want, so the
rule permits it rather than forcing reviewers to discard their evidence or launder it
through their return value.

### Enforcement, and where it is NOT

- **Enforced by:** a **PreToolUse hook keyed on `agent_type`** —
  `.claude/hooks/role-write-scope.py`, invoked through `.claude/hooks/run-hook.cmd`, wired
  in `.claude/settings.json`. Prevention, not detection. Three policy classes:
  `dream-reviewer-*` and `dream-ledger-auditor*` may write only under `.program/audits/**`;
  `dream-reader-*` and `dream-verifier*` write nothing anywhere; every other role is
  short-circuited before any analysis and is never restricted.
- **Detected by:** auditor **check 13** as defence-in-depth (see ADR-0014 §check 13 below),
  and auditor **check 14**, which fails BLOCKING if the hook left no trace at all in the
  session under audit (see §Heartbeat).
  Prevention alone was judged insufficient because the command-analysis layer cannot be
  proven exhaustive — `tee` already defeated one path-based rule (see below).
- **NOT enforced by deny rules in `.claude/settings.json`.** Deny rules were the original
  plan and are the wrong instrument, for **two independent reasons**:
  1. **Scope.** Permission rules are *session-wide*. They apply to every agent in the
     session with no way to name one. A rule expressing "reviewers may not write `src/**`"
     would equally forbid the director from writing the ledger and implementers from
     writing source. The rule cannot say "reviewers only", so it cannot express this
     guarantee at all.
  2. **`Write(path)` is inert.** Only `Edit(path)` rules are matched by file permission
     checks; a `Write(...)` rule silently matches nothing. The CLI emits an explicit
     warning saying so. Had this gone unnoticed, the `.env*` and `.git/**` protections in
     the global block would have been decorative.
- **The `tee` leak is why detection stays alongside prevention.** In A/B probing, a
  path-based `Edit()` deny rule was bypassed by `printf x | tee <path>` — the
  command-analysis layer does not recognize every write vector. The hook enumerates ~30
  write verbs, but an enumeration is a denylist and denylists are never provably complete.
  Check 13 catches what the enumeration misses, after the fact.
- **Never enforced by:** the `tools:` declaration in a role file. Recording this
  explicitly because the previous design believed it was, and that belief is what let a
  structurally-absent guarantee go unnoticed across 38 generations.
- Prose in a role file remains useful as instruction — agents did in fact respect it — but
  it is a request, not a boundary. The distinction matters when writing future guarantees:
  if a claim of the form "this agent cannot X" appears anywhere, there must be a deny rule
  behind it or the claim is false.

### Was it exercised?

No. Established by sweeping all 125 subagent transcripts with per-record
`attributionAgent` (necessary because the relauncher's `git add -A` destroyed git
attribution — ADR-0012). Across every dispatch of the five roles: zero writes to any
artifact under review, any ledger item, or any source file; zero memory writes (all three
`.claude/agent-memory/` directories were empty, 0 files, now deleted); one scratch probe
written and self-deleted 7 seconds later outside the artifact; the four
`.program/audits/**` captures described above; and one `mv .next .next.backup` **denied**
by the permission system. Review independence is intact and all 13 `done` items keep their
verdicts — a `review_guarantee_breach_unexercised` event records this on each.

## Operating the hook — findings that cost a session each

These are recorded because every one of them was learned by breaking the session, and each
would be re-learned the same way by anyone editing this hook.

### The guard split: fail closed on the command, fail open on the hook

Two kinds of uncertainty, opposite defaults:

- **Uncertain about the COMMAND, hook working → DENY.** A restricted role issuing something
  the analyzer cannot decompose does not get the benefit of the doubt.
- **Uncertain about the HOOK — bad payload, internal exception, any bug → ALLOW, and log
  it.** This hook runs on every `Write`/`Edit`/`Bash`/`NotebookEdit` call by every agent. A
  hook that fails closed on its own bug is not a safety measure, it is a total program
  outage. Verified by injecting a `RuntimeError` into `decide()`: exit 0, valid `allow`,
  failure logged.

### Lockout recovery requires an external shell — so standalone verification is a prerequisite

**Non-zero exit or empty stdout from a hook is treated as BLOCK.** This happened: the hook
was wired into `settings.json` before the policy script existed. Python exited 2 on the
missing file, so *every* `Write`/`Edit`/`Bash` call was denied — including the ones needed
to fix it — and the new `Edit(**/.claude/settings*.json)` deny rule closed the other route.
The session could not repair the file that was breaking it. Recovery came from the owner
running a command in an **external shell**.

Therefore: **verifying a new version of this script standalone, from outside the session,
before referencing it from `settings.json`, is a hard prerequisite — not a good practice.**
`.claude/hooks/zz-verify-hook.py` exists for exactly this and runs the script as a real
subprocess with real stdin (81 cases: three policy classes, every Bash vector, traversal,
absolute paths, empty/missing command, and four hook-failure cases).

### The interpreter chain, and why there is a launcher

Two failure modes kill the interpreter **before any Python runs**, so no in-script guard can
ever cover them: a **missing script** (python exits 2) and a **syntax error** (exits 1).
Those were the lockout. The launcher's entire purpose is to convert "interpreter or script
unavailable" into an explicit `allow` and always exit 0 — something only an outer process
can do. Verified by deleting the policy script and confirming the launcher still returns a
valid allow with 0 bytes on stderr.

Resolution on this machine, established empirically:

| Interpreter | Reality |
|---|---|
| `python` | `C:\Python314\python.exe` (3.14.0) — works |
| `python3` | **Microsoft Store shim**: prints "Python was not found", exits non-zero |
| `py` | `C:\WINDOWS\py` |
| `sh` | **EXISTS** at `C:\Program Files\Git\usr\bin\sh.exe`, reachable from the hook's shell |
| `cmd.exe` | always present |

`C:\Python314\python.exe` is **hardcoded** in `run-hook.cmd`, deliberately: a PATH lookup is
exactly the environment dependency that bricks this, and `python3` in particular would have
re-bricked the session *with the file present and correct* — a far more confusing failure
than a missing file. If Python moves, update that line.

**Correction to an earlier finding in this program: `sh` does NOT fail to exist.** The
"`sh` does not exist on this machine" claim came from **PowerShell's PATH**, where the
Git-for-Windows `usr/bin` entry is absent. From the hook's actual shell it resolves fine.
That single bad inference is what produced the `cmd` wrapper and the entire detour below.
The lesson generalizes past this hook: **resolve an interpreter in the shell that will
actually invoke it, not in whatever shell happens to be open.**

### MSYS path conversion mangles single-slash flags — the durable Windows trap

**Hooks are spawned through git-bash.** MSYS argument conversion rewrites anything that
looks like a Unix path, so a single-slash Windows flag is silently destroyed:

```
"command": "cmd /c \"${CLAUDE_PROJECT_DIR}\\.claude\\hooks\\run-hook.cmd\""
```

`/c` was converted to a path, cmd never received the flag, and **cmd started interactively**
— printing its banner and consuming the JSON payload as typed input (visible as cmd's
`More?` continuation prompt). The hook fired 49 times and returned no parseable decision
every time; the harness read that as allow, and a live reviewer probe wrote four
out-of-policy files with zero denials logged.

`${CLAUDE_PROJECT_DIR}` interpolation was never the problem. The fix is either `cmd //c`
(MSYS collapses `//` to `/`) or, as adopted, **no shell wrapper at all** — bash can execute
a `.cmd` directly:

```
"command": "\"${CLAUDE_PROJECT_DIR}/.claude/hooks/run-hook.cmd\""
```

**Anyone later adding a Windows-shell wrapper to a hook on this machine hits this again.**
The diagnostic signal is a `Microsoft Windows [Version ...]` banner in the transcript's
`hook_success` attachment content: a correctly-invoked `cmd /c` prints no banner, so the
banner *is* the bug. Absence of the banner (empty content) is what confirms the launcher is
actually being reached.

### Workspace trust gates the whole mechanism

`hasTrustDialogAccepted` for this workspace in `C:\Users\jainv\.claude.json` controls whether
`.claude/settings.json` is honoured **at all** — `permissions.allow` with a visible warning,
`hooks` silently. It was `False` while this ADR was first written, which meant a *fresh*
session dropped both the deny rules and this hook. **The owner granted trust on 2026-07-27**
and enforcement was then re-verified in genuinely fresh sessions (see the table below).

The durable finding is the silence, not the flag: a `False` here removes the hook with **no
warning of any kind**, while the permissions half at least prints one. Anything that depends
on this hook must therefore verify liveness from an artifact rather than assume it — which is
what the heartbeat and check 14 are for.

### Heartbeat: allows are logged too, because zero denials is ambiguous

**Finding credited to `dream-reviewer-primary`.** Asked to probe its own deny branch, it
declined — correctly, on the grounds that authorization relayed through an agent message is
not its user's consent, and that "attempt it so we can see if the guard works" is still an
attempt. Then it identified the real defect unprompted:

> Self-restraint and a hook denial are indistinguishable in the evidence log. When a role
> declines, nothing is written, and a later reader cannot tell whether the hook is enforcing
> the rule or is silently broken and merely got lucky with a well-behaved agent.

That is exactly the failure that already happened: 49 invocations returned unparseable output,
every one read as allow by the harness, recorded nowhere. The reviewer's proposed fix — have
the hook log allowed calls too — is adopted:

- One **heartbeat** row per `(session_id, agent_id)`, on a restricted role's first ALLOWED
  call. Rows carry `kind: "heartbeat"`; denials now carry `kind: "denial"`.
- The claim is atomic (`os.open(O_CREAT|O_EXCL)` on a marker under
  `.program/audits/.heartbeat-state/`, gitignored) so concurrent calls from one agent cannot
  emit duplicates.
- **Restricted roles only.** Implementers, coordinators and the director short-circuit before
  this point. They generate the bulk of all tool calls and logging them would bury the signal.
- Presence proves the hook ran for that role in that session. Absence is now a *finding*
  (check 14) rather than an absence of evidence.

**Known limit, observed rather than reasoned:** the matcher is `Write|Edit|NotebookEdit|Bash`,
so a restricted role working purely through `Read`/`Grep`/`Glob` never reaches the hook and
emits nothing. A live reviewer answering a question from `Read` alone produced no row. Absence
therefore means "no matched tool call was seen", not "the role did nothing" — check 14 must
inspect the role's tool calls before treating absence as failure. Closing this would mean
matching every tool, which trades a large volume of noise for a small gain.

Also fixed while here: `DENIAL_LOG` was **cwd-relative**, so a worktree implementer or any
agent that `cd`'d elsewhere would have scattered evidence into a second tree. It now resolves
relative to the hook file. A misplaced evidence log is worse than none once absence is read as
failure.

## Consequence

Corrections applied to the record, so no document claims a guarantee that does not exist:

- All five role files: the `description:` line and the "Hard stops" line now state the
  narrowed rule and name Bash as the reason, instead of asserting read-only.
- The claim "you have no Write, Edit or Agent tool" is replaced by "do not write outside
  `.program/audits/**`" — a rule an agent can actually comply with, and one that stays
  true if the tool set changes again.
- `dream-reader-lookup` keeps its stronger claim: it has no Bash, so it is genuinely
  read-only. `dream-reader-corpus`, `dream-verifier`, `dream-verifier-deep` have Bash and
  are corrected the same way as the five.
- **The gap is closed.** The narrowed guarantee was prose-only when this ADR was first
  accepted; it is now enforced by the hook above and detected by check 13. Verified by live
  dispatch on 2026-07-27, by ground truth rather than self-report:

  | Role class | Vector | Target | Result | On disk |
  |---|---|---|---|---|
  | `dream-reviewer-primary` | redirect | `.program/audits/…` | allowed | present |
  | `dream-reviewer-primary` | redirect, `tee`, `cp`, `python -c` | repo root | **denied ×4** | absent ×4 |
  | `dream-verifier` | redirect ×2, `tee` | anywhere incl. audits | **denied ×3** | absent ×3 |
  | `dream-implementer-standard` | Write, Edit, redirect | repo root | allowed ×3 | present |

  All seven denials appear in `.program/audits/hook-denials.jsonl` with the real
  `session_id` and per-agent `agent_id`. **Implementers, coordinators and the director are
  unaffected** — tested explicitly, because an over-broad hook blocking implementer writes
  would present as task failure rather than as a hook problem and would be expensive to
  diagnose during a live run.

- **Re-verified in genuinely fresh sessions after trust was granted (2026-07-27).** The table
  above was produced inside the session that built the hook, which proves the policy but not
  that a new session loads it. Re-run as separate processes, each with its own `session_id`:

  | Fresh-session check | Evidence |
  |---|---|
  | No "Ignoring N permissions.allow entries" warning | clean stderr on a fresh `claude -p` |
  | Hook loads at all | session `0a02180a`: 1 Bash call → 1 `hook_success`, empty content, no banner |
  | `dream-verifier` denied | denial row, session `5aa61865…`, agent `a0a7d0cec9e9bf686`, file ABSENT |
  | `dream-implementer-standard` unimpeded | wrote `zz-fresh-impl.ts` (32 b), zero denial rows |
  | `dream-verifier` heartbeat | session `6bf45fe0…`, agent `ae4dc0196afb0688b`, read-only call |
  | `dream-reviewer-primary` heartbeat | session `8f90f1ed…`, agent `abc7407389f7fed04`, read-only call |

  The two heartbeats close what the denial table could not. **No live `dream-reviewer-primary`
  has ever been stopped by this hook** — it self-declined every time it was asked to try, so
  its deny branch is proven only at the policy layer (all six role×target combinations
  exercised directly against the hook, 3 denial rows, 0 files created) and by the verifier's
  live denial. The heartbeat confirms the hook is live *for that role* in the meantime, which
  is the honest substitute. It will resolve on its own the first time a real reviewer attempts
  a write outside `.program/audits/**` during actual work. Tracked in `DECISIONS-PENDING.md`;
  **do not manufacture a test for it.**

## Appendix — the ToolSearch discrepancy, resolved

Phase 2 produced two apparently contradictory readings: the role files declare
`tools: Read, Grep, Glob, Bash, ToolSearch` for the three reviewers, but the runtime tool
list showed only `Read, Grep, Glob, Bash`.

**Both were accurate reports of different things, and the runtime one is the operative
truth.** Re-probed on 2026-07-26 by dispatching all three reviewers with a diagnostic
prompt asking them to enumerate their own tools without using any. All three returned,
independently and identically:

```
Read, Grep, Glob, Bash
ToolSearch: ABSENT
```

So: **ToolSearch is declared in the frontmatter and not granted at runtime.** Nothing was
changed to make the two agree — the declaration is left in place deliberately, because the
discrepancy is itself a finding: a name in a `tools:` list is a request, and the runtime
grant is the fact. This is the same lesson as the body of this ADR from the opposite
direction — `memory:` added tools that were not declared, and `ToolSearch` was declared but
not added. **The frontmatter `tools:` list is neither a floor nor a ceiling. Never reason
about an agent's capabilities from it; enumerate at runtime.**

Practical consequence: the three reviewers cannot reach deferred/MCP tools. Nothing in the
38 generations depended on that — every reviewer check ran through Bash — so no verdict is
affected. If a reviewer is ever given work that needs ToolSearch, verify the grant with a
probe first rather than trusting the declaration.

## If wrong

If a reviewer is ever found to have written outside `.program/audits/**`, the deny rules
are incomplete — check Bash redirection and heredoc forms first, since those are what a
Write/Edit-shaped deny rule misses. If a reviewer's verdict is ever suspected of
contamination, the transcripts are the evidence of record, not git: per-record
`attributionAgent` gives exact per-agent attribution and survives the loop's sweeping
commits.
