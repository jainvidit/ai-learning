# ADR-0025: REQ-EX-01 s3 "never branches on driver" — ratification as falsifiable via grep

**Status:** Ratified  
**Date:** 2026-07-28  
**Context:** ADR-0018 enumeration schedule; unfalsifiable-criteria survey (2026-07-27T0540) classified execution-layer REQ-EX-01 s3 as borderline  
**Decider:** implementer-ROOT.7.3.7-gen0

---

## Decision

RATIFY REQ-EX-01 scenario 3 as **falsifiable as written** via a concrete grep-based check. The driver count is fixed at 2 (LocalDriver, CloudDriver; CloudDriver interface-only per ADR-0001), and both are named in the spec. The no-branching guarantee can be verified by grepping src/ for driver-type conditionals and classifying hits.

No shard edit required. The scenario text ("Given the terminal/dock UI code, when audited, then no rendering or behavior branches on which driver is active") is testable as written.

---

## Concrete falsification procedure

**Check:** grep src/ for driver-conditional code patterns.

**Patterns (ripgrep):**
```
rg '(instanceof\s+(LocalDriver|CloudDriver|ExecutionDriver))|(driver\s*[!=]==?\s*(Local|Cloud))|(driver\.type|driver\.kind|DRIVER_TYPE|EXECUTION_DRIVER)' \
  --type ts --type tsx \
  --glob 'src/**' \
  --ignore-case
```

**Covered conditionals:**
1. `instanceof LocalDriver`, `instanceof CloudDriver`, `instanceof ExecutionDriver` — class-instance checks
2. `driver === Local`, `driver !== Cloud`, etc. — string/enum equality against driver kind
3. `driver.type`, `driver.kind`, `DRIVER_TYPE`, `EXECUTION_DRIVER` — field/constant references that would enable branching

**Paths in scope:** `src/` (all TypeScript/TSX, recursively) — the entire client and server application code outside of specs/docs.

**Allowed exceptions (composition/factory):**
- **src/lib/execution/factory.ts** (or equivalent): the driver-selection factory MAY branch on a config/env var to instantiate the correct driver. This is the single composition point where driver choice happens, per the factory pattern.
- Exception rule: a file MAY contain driver-type conditionals if its sole purpose is driver instantiation/selection. Any other file branching on driver type is a FAIL.

**Pass/Fail classification:**
- **PASS:** Zero hits, or hits only in the allowed factory file (composition point).
- **FAIL (definitive):** Any hit in UI code (src/components/, src/app/), API routes other than the factory, or lib/ modules consumed by UI.
- **Conservative FAIL (disputed):** If a hit is ambiguous (e.g., in a util that both factory and UI consume), escalate to adversarial review. The conservative stance is FAIL — the burden is on the code to prove it's not a UI-visible branch.

---

## Baseline dry-run (2026-07-28, commit e52164a)

Ran the grep procedure over current src/:

**Result:** PASS (zero hits on driver-conditional patterns)

- No `instanceof LocalDriver/CloudDriver/ExecutionDriver`
- No `driver === Local/Cloud` or `driver.type`/`driver.kind` field accesses
- No `DRIVER_TYPE` or `EXECUTION_DRIVER` env checks in src/

**Observations:**
- `src/lib/claudeSpawn.ts` hardcodes the LocalDriver behavior (spawns the real claude.exe) but contains no conditional that compares driver types — it is the current pre-abstraction implementation.
- UI code (Terminal.tsx, exec/route.ts) calls `spawnClaude` and `claudeAvailable()` without referencing driver types or conditionals.

**Conclusion:** The current codebase satisfies REQ-EX-01 s3 as written. The grep check is ready for use when ROOT.4.5 implements the ExecutionDriver abstraction.

## Closed-world / relaxation rules

**Closed-world:** The two driver names (LocalDriver, CloudDriver) are fixed in execution-layer.md REQ-EX-01 and are unlikely to expand. If a third driver is ever added (e.g., "MockDriver" for testing), the grep pattern MUST be updated to include it.

**Relaxation:** None. The no-branching guarantee is absolute for UI/rendering code per LANE-DEPENDENCIES row (execution-layer, depended on by terminal-experience.md: "Nova's dock UX must not branch on driver"). The factory may branch to compose; nothing else may.

**Pattern updates:** If ROOT.4.5 introduces a driver-selection mechanism that does NOT use the strings "LocalDriver"/"CloudDriver" (e.g., a symbol, a numeric constant), the grep pattern must be updated to cover that mechanism. The implementer of ROOT.4.5 MUST verify the pattern still covers the shipped abstraction.

---

## Shard edit ruling

**No shard edit required.** REQ-EX-01 scenario 3 is falsifiable as written:  
> "Given the terminal/dock UI code, when audited, then no rendering or behavior branches on which driver is active."

The grep-based check operationalizes "when audited" as a concrete grep command, and the pass/fail rules operationalize "no rendering or behavior branches" as zero hits in UI code. The scenario does not need additional text — the falsification procedure is recorded here in the ADR per the enumeration pattern established in ADR-0017 and ADR-0028.

## Maintenance

If ROOT.4.5 (or any future Phase-3 work) changes the driver abstraction or adds a third driver:
1. Re-run the baseline dry-run grep
2. Update this ADR's pattern list if the abstraction uses different names/fields
3. Re-verify that the factory is the sole composition point

This check is a one-time ratification, not a recurring gate. The pattern is intended for use by ROOT.4.5's acceptance criteria and any future audits disputing REQ-EX-01 s3 conformance.
