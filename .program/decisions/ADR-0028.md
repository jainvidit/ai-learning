# ADR-0028 — REQ-MS-03 s1 delete-verb list canonicity ruling

Date: 2026-07-27. Author: implementer-ROOT.7.3.10-gen0.
Status: ratified.
Spec ref: .program/spec/migration-and-sequencing.md#req-ms-03 scenario 1.

## Context

The unfalsifiable-criteria survey (.program/audits/2026-07-27T0540-unfalsifiable-
criteria-survey.md) classified REQ-MS-03 scenario 1 as "borderline" because the delete-
verb list is enumerated in the requirement text but not explicitly ruled canonical. The
survey note: "zero hits over delete verbs — verb list enumerated in the requirement,
falsifiable if canonical."

The requirement guards `data/**`, the Workshop directory (`sandbox/live/**`), and
`docs/origin/**` from all deletion paths. The Phase Gates (ROOT.1.8, 2.5, 3.6, 4.9, 5.6)
will run this check as a falsifiable MS-03 row.

The spec's enumerated verb list (migration-and-sequencing.md line 71) is:
> `rm`, `rmdir`, `unlink`, `rmtree`, `Remove-Item`, `fs.rm`, `fs.unlink`, `del`, `truncate`

## Decision

1. **The list as written is INCOMPLETE.** Empirical testing (2026-07-27) found six
   instances of `fs.rmSync` in current code (`scripts/build-content-bundle.ts`,
   `scripts/seed-sandboxes.ts`, `src/lib/profiles.ts`, `src/lib/sandbox.ts`) that would
   be missed by the spec's list. The list names `fs.rm` and `fs.unlink` but omits their
   sync variants and the common `fs.rmSync` method.

2. **Completed canonical list** (closed-world, exhaustive):
   - **Shell/Python**: `rm`, `rmdir`, `unlink`, `rmtree`, `Remove-Item`
   - **Node.js fs methods**: `fs.rm`, `fs.rmSync`, `fs.rmdir`, `fs.rmdirSync`, `fs.unlink`, `fs.unlinkSync`
   - **Generic**: `del`, `truncate`
   - **npm packages**: `rimraf` (common deletion utility)
   
   Rationale per verb:
   - `fs.rmSync` / `fs.rmdirSync` / `fs.unlinkSync`: sync counterparts to async methods;
     already present in codebase.
   - `fs.rmdir`: async counterpart to `fs.rmdirSync`; omitted from original list.
   - `rimraf`: widely-used npm package for cross-platform recursive deletion; not present
     in current codebase but common enough to guard against.
   
   Rejected candidates:
   - `remove`: too generic (matches CSS class names, comment text); the specific methods
     (`fs.rmSync`, `rimraf`) provide sufficient coverage.
   - `drop`: SQL-specific; this program guards file trees, not database tables.

3. **The grep procedure for every phase Gate** (ROOT.1.8, 2.5, 3.6, 4.9, 5.6):

   ```bash
   grep -rn '\brm\b|\brmdir\b|\bunlink\b|\brmtree\b|Remove-Item|fs\.rm\b|fs\.rmSync|fs\.rmdir|fs\.rmdirSync|fs\.unlink|fs\.unlinkSync|\bdel\b|\btruncate\b|\brimraf\b' \
     --include="*.py" --include="*.js" --include="*.ts" --include="*.tsx" --include="*.json" \
     .program/ scripts/ src/ \
     2>/dev/null \
     | grep -v node_modules | grep -v '.program/ledger/' | grep -v 'test\|spec\|__tests__'
   ```
   
   **Exclusions:**
   - `node_modules/`: third-party code outside program control.
   - `.program/ledger/`: the append-event.py script uses `os.unlink` on its own temp
     files (ADR-0015 temp-file staging pattern); this is an allowed exception.
   - Test/spec/fixture files: tests may delete their own fixtures; only production code
     paths are guarded.
   
   **Hit classification:**
   - **PASS**: zero hits, OR all hits are in test files, OR all hits target paths outside
     the protected trees (provable by inspection).
   - **FAIL**: one or more hits target `data/**`, `sandbox/live/**`, or `docs/origin/**`.
   - **FAIL (conservative)**: a hit whose target is a variable or glob that *could*
     resolve into a protected tree. The requirement states "fails closed" — ambiguity is
     a failure, not a pass.
   
   **Exception recording:** if a hit is ruled allowed (e.g., a migration script deleting
   its own staging area), the Gate evidence doc must name the file, line, and
   justification. Repeat exceptions (same file/line across multiple gates) cite the first
   Gate that approved them.

4. **Closed-world rule:** any deletion verb not on this list is implicitly allowed. Adding
   a new guarded verb requires an additive ADR amending this decision.

5. **Relaxation path:** if a future phase needs to delete within a protected tree (e.g.,
   archival per REQ-MS-03 s2, or Workshop cleanup), the work is PARKED
   (`DECISIONS-PENDING.md`, `awaiting_human_authorization` status) until owner approval,
   then an additive ADR records the specific exception (file, function, target path).

## Notes and readings considered

- The survey's "falsifiable if canonical" condition is met: this ADR rules the list
  canonical (as completed), and every Gate will run the same grep.
- The baseline violations are findings, not fixes. The ADR's role is to make the criterion
  falsifiable; remediation is the work of the capabilities that own profiles.ts and
  sandbox.ts.
- The fail-closed rule ("a variable that *could* resolve into a protected tree is a FAIL")
  matches the REQ-MS-03 text and is necessary for enforcement — a profile-deletion path
  that takes `id` as a parameter and constructs `data/progress/${id}.json` FAILS the
  check even if no call site currently passes a value that triggers it.

## Reversal path

If future evidence shows the completed list is over-broad (e.g., `truncate` drowns every
grep in CSS false positives), an additive ADR can remove a verb from the canonical list or
refine the grep pattern. Additions to the list remain additive-only.
